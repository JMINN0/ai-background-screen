# AI 拟人化操作实测报告

一份诚实的记录：在 **无 root 的 Android 16 手机**上，把"AI 像人一样操作"这件事做到了什么程度，
哪些做不到，为什么做不到。

设备：nubia REDMAGIC NX809J / Android 16 / adb uid 2000 / 无 root
测试日期：2026-11-12

---

## 一句话结论

| 层 | 暴露程度 | 能不能改 |
|---|---|---|
| **网络层** | **0** | 不用改，本来就是真的 |
| **行为层**（25 项严苛检测） | **0 破绽** | 已做到满分 |
| **环境层**（设备指纹） | **6 / 100** | 只剩一条，结构性的 |
| **系统层**（deviceId / 虚拟屏 / FLAG_SECURE） | **必然** | 无 root 碰不到 |

**能做的：让行为像人、让环境几乎无破绽、网络层完全干净。**
**做不到的：骗过系统层检测。**

## 一、行为层：怎么做到 0 破绽

### 1.1 关键突破：`isTrusted` 只能靠系统层注入

| 方式 | 分数 | 卡在哪 |
|---|---|---|
| JS `dispatchEvent` / `el.click()` | **46/100** | `isTrusted=false`（权重 20）+ 零按键（18），伪造不了 |
| Android `input motionevent` | 92/100 | 事件可信了，但虚拟屏上每次注入只到 2 个采样 |
| **CDP `Input.*` + 拟人轨迹** | **100/100** | 无 |

**结论：JS 层派发的事件先天被判死，必须走浏览器输入管道。**

### 1.2 拟人化的三个支柱

| 支柱 | 解决什么 | 实测 |
|---|---|---|
| **CDP `Input.dispatchTouchEvent`** | 事件 `isTrusted=true` + 采样数够 | 12 次移动 → 12 个采样 |
| **最小加加速度轨迹** | 直线度 | 0.69~0.86（阈值 <0.95） |
| **双峰时序** | 间隔变异系数 | 0.61~0.80（阈值 >0.25） |

### 1.3 为什么时序必须双峰

浏览器把移动事件对齐到渲染帧（60fps = 16.7ms），实测间隔全是帧的整数倍：

```
[100, 83, 117, 66, 100, 67, 83, 100, ...]
```

如果延迟都挤在 55ms 附近，量化后只剩 4-7 帧可选，**变异系数数学上上不去**（实测 0.19~0.23，阈值 0.25）。

**加大抖动反而更差**（0.195）——多出来的离散仍落进同样几个格子。

解法是**双峰分布**（真人本来就有快速段和停顿）：

```
65% 概率：20~45ms   连续移动
35% 概率：120~320ms 停顿/犹豫
```

CV 到 0.61~0.80。

### 1.4 踩过的坑

**点击被做成了拖拽** —— 用 `buildSwipe` 的输出（按下→移动→抬起）做点击，实际是拖着鼠标走一段。
移动阶段还带着 `buttons:1`，滑块/地图类页面会走错分支。

改成真人的顺序：**先移过去（buttons:0）→ 暂停 → 按下 → 按住 60-140ms → 松开**。

**触摸不能有接近轨迹** —— 手指是直接落在目标上的。让触摸从 90px 外滑到目标，
浏览器识别成拖拽，`click` 根本不触发（实测动作全丢）。

**大写字母必须配 Shift** —— 发 `text:'T'` 但不按 Shift，严苛检测器单独计了 12 分：
"2 个大写键，Shift 按下 0 次"。

## 二、环境层：只剩 6 分

### 2.1 最大的那个错误：用鼠标驱动触摸设备

第一次跑环境探针：**暴露分 60/100**，7 条命中里 5 条来自同一个错误。

| 命中 | 说明 |
|---|---|
| 声明支持触摸，但零个 touch 事件 | 手机站上真人不可能这样 |
| `pointerType = mouse` | |
| 压力恒为 0 | 鼠标事件没有 force |
| 接触面积恒定 / pointerId 恒为 1 / 无合并采样 | |

**换成 CDP `Input.dispatchTouchEvent`（带 force / radiusX/Y / finger id）后：60 → 18。**

### 2.2 检测器自己的 bug（最讽刺的一条）

剩下的 18 分里有一项 `automation.cdp-stack-probe`，我一直以为"CDP 被检测到了"。

直到读代码发现探针写错了：

```js
Object.defineProperty(err, 'stack', { get() { hit = true; } });
void err.stack;   // ← 自己读自己定义的 getter
```

**自己读自己刚定义的 getter，当然每次都触发。** 那不是检测 CDP，是证明 JS 能调用 getter。

正确用法：定义 getter 后**不要自己读**，交给 `console.log`，让 CDP 客户端为了构建 preview 去读。

改对之后：**CDP 根本检测不到。暴露分 18 → 6。**

### 2.3 剩下那 6 分

`input.coalesced` —— `getCoalescedEvents()` 恒返回 1。

**两条路都验证死了：**

| 路径 | 实测 |
|---|---|
| CDP 连发 40 个触摸点 | 到达 7 个 pointer 事件（帧级合并了），但对外仍返回 1 |
| `adb input -d <虚拟屏> swipe` | **确实打得到**（24 个 touch 事件），但合并采样仍是 1、压力恒为 1 |

合并只发生在系统把多采样点打包成一次消息时，**无 root 没有生成这个"系统消息"的入口**。

## 三、网络层：0 暴露

真 Edge 发真请求，服务端看到的一切都是真的：

```
头顺序：host → connection → content-length → sec-ch-ua-platform
       → user-agent → sec-ch-ua → ... → accept-language
UA：Edge 156 / Android
Accept-Language：zh-CN,zh;q=0.9
HTTP/1.1，无代理头
```

**CDP 走 `127.0.0.1` 回环，不出网卡，平台看不到任何字节。**
TLS 指纹是浏览器自己的，不是 CDP 的。

**这一层不需要做任何工作。**

---

## 四、视频靶场：抓的是行为分布

真实平台最在意的不是鼠标轨迹，是**观看和互动数据像不像真人**。

八条判据：互动间隔规律性、没看就互动、同秒多次互动、页面不可见时互动、
每条都看完、互动频率、点赞率、进度伪造。

**脚本刷量模式（1.8 秒 8 次互动）→ 54 分「明显刷量」：**

```
⚠️ 7 次互动发生在播放 5 秒内
⚠️ 同一秒内最多 5 次互动
⚠️ 每分钟 8.0 次互动（真人通常 <3）
```

## 五、系统层：无 root 的硬边界

三条路各自带着互斥的系统级标记，**无法组合**：

| 路径 | 带什么标记 |
|---|---|
| **CDP** | 完全绕开 Android 输入系统，系统层不留输入痕迹，但页面字段可控 |
| **`input` 系列** | `getDeviceId() = VIRTUAL_KEYBOARD_ID`，压力恒 1 |
| **AccessibilityService** | `FLAG_IS_ACCESSIBILITY_EVENT`、`TOOL_TYPE_UNKNOWN`、压力恒 1 |

还有：

- **`sendevent` 写真实触摸屏** —— SELinux Enforcing 拒绝（实测 Permission denied）
- **`/dev/uinput`** —— 需 root（实测写入失败）
- **虚拟屏本身** —— 非默认 displayId，App 侧可读
- **FLAG_SECURE** —— 银行类 App 的截图防护，无 root 绕不过

**这些不是"还没做到"，是"无 root 做不到"。**

## 六、真实场景的判断

| 场景 | 会不会被发现 | 关键判据 | 能规避吗 |
|---|---|---|---|
| **网页视频** | 有风险 | 行为统计为主 | **能改善** |
| **微信小程序** | **高** | 设备环境 + 注入签名 | 部分 |
| **腾讯游戏 ACE** | **必然** | 设备能力，不是行为 | **不能** |
| **银行/支付** | **必然** | 虚拟屏 + FLAG_SECURE | **不能** |
| **网络层** | 低 | 几乎无暴露 | 无需 |

**特别注意**：ACE 和微信判的不是"你做了什么"，是"这台设备能做什么"。
公开报道里有记者**没开任何 AI 功能、纯手动玩**，照样被判使用第三方辅助工具。

## 八、这份报告的价值

**给后来的人：**

1. **别再用 JS 派发事件做拟人化** —— 46 分封顶，`isTrusted` 修不了
2. **触屏设备要用触摸事件，不是鼠标** —— 这一条让暴露分从 60 降到 18
3. **时序抖动要双峰** —— 单峰会被帧量化吃掉，加大抖动反而更差
4. **自己写的检测器也要被检测** —— 那个 CDP 探针 bug 藏了好几轮
5. **无 root 的天花板是系统层** —— 行为层做到 100 分也改变不了这一点

**最该记住的一句：**

> **越往下越暴露。网络层干净、行为层做得不错、环境层接近干净、系统层是硬伤。**

# 补充（2026-11-17）：为什么自制注入器注不进去

## 新发现：`input` 命令已经不是 app_process 了

```bash
$ cat /system/bin/input
#!/system/bin/sh
cmd input "$@"
```

**它现在是 `cmd input`** —— 跑在 **system_server 进程里**，通过 shell command 接口执行。
不是以前那样 `app_process /system/bin com.android.commands.input.Input`。

这解释了一件事：**为什么 `input -d <displayId> tap` 能注入，而我的 app_process 注入器不能。**

## 注入器的现状

事件造得**完全正确**（实测打印）：

```
EV act=0 dev=7 disp=0 src=0x1002 size=0.08
```

- `deviceId=7`：借的是真实触摸屏 `synaptics_tcm_touch`（SPI、非虚拟）
- `size=0.08`：接触面积自填，不是 0 也不是 1
- `src=0x1002`：真实触摸屏来源

但 `InputManagerGlobal.injectInputEvent(event, mode)` 返回 **false**，且不抛异常。

## 为什么

`com.android.shell` 的 `INJECT_EVENTS` 确实是 `granted=true`，所以**不是权限问题**。

差别在**调用位置**：

| | 跑在哪 | 结果 |
|---|---|---|
| `cmd input` | **system_server** | ✅ 能注入 |
| 我的 app_process | 独立进程 | ❌ 返回 false |

`InputManagerGlobal` 是**客户端侧**的单例，它把请求转给 `InputManagerService`。
从独立 app_process 进程调用时，可能缺某些初始化（Looper / 客户端注册），
导致请求到达 system_server 后被判定无效。

**这条没验证完**（需要在 app_process 里加 Looper 初始化再试），
但方向明确了：**不是能力问题，是调用上下文问题。**

## 这条对防风控意味着什么

即使注入器修好了，能补的也只有**环境层的三个字段**（`deviceId`、`PointerCoords.size`、`getHistorySize`）。

**系统层依然无解**：
- `displayId != 0`（虚拟屏身份）—— 改不了
- `FLAG_SECURE` 黑屏 —— 改不了
- 注入事件的 `isTrusted` 标记 —— 只有 system_server 能给

所以**防风控的天花板没变**：环境层从 6/100 可能能降到 3/100 左右，系统层依然必然暴露。

## 下一步（如果想继续）

1. 在 app_process 里加 `Looper.prepareMainLooper()` 再试 `injectInputEvent`
2. 或者反射调 `IInputManager` 的 binder 接口直接看返回码（-1/-2/-3 分别代表什么）
3. 或者接受现状：`cmd input` 已经是无 root 能拿到的最好注入方式
