# PK：我们 vs `dsh-video-storyboard`

> 分轨评分，不设综合分。两件事。
> 测于 2026-11-16。素材：`S3SeasonCG.mp4`，1536×864，30fps，166.37 秒。

## 一、素材

```
文件: /tmp/pk/S3SeasonCG.mp4
时长: 166.37 秒（2.8 分钟）
分辨率: 1536×864
帧率: 30fps
大小: 67MB
内容: 3D CG 动画（动态丰富，镜头切换频繁）
```

## 二、storyboard 侧的真实成本（它自己的 dryRun 报的）

```
切点数: 49（平均 3.4 秒一个镜头）
帧数: 82
画布: 798×443 → 222 vision token / 图
```

| 策略 | 图片数 | 图片 token | 说明 |
|---|---|---|---|
| skim | ≤2 | ≈ 444 | 1/8 格，合并切点 |
| compact | 7 | ≈ 1,554 | 每帧降一档 |
| standard | 10 | ≈ 2,220 | tier 1 缩到 1/2 |
| **full** | **48** | **≈ 10,656** | **它推荐这个** |

**加文本索引**（`detail=med` 每格 120 字符，82 格）→ 约再 2,000-4,000 token。

**小计：读懂这 2.8 分钟，storyboard 走 full 约 12,000-15,000 token。**

值得注意的是它自己的手册写着：「**Never pass "full" as a safe default** —— 它是最贵的设置，
不是最完整的」，但在 49 个切点的情况下 auto 还是选了 full。

## 三、我们侧的成本

我们的计价：

| 形态 | 尺寸 | token |
|---|---|---|
| region 局部（≤544²） | 420×420 | **169（地板价）** |
| 全屏 420 宽 | 420×929 | 230 |
| 九格单格 | 262 宽 | ≈89 |
| **九格整张（9 帧）** | 3×3 | **798** |

**同样看 48 个关键时刻：**
- 全用 region 裁切：48 × 169 = **8,112 token**
- 用 6 张九格（54 帧）：6 × 798 = **4,788 token**

**比 storyboard 的 12,000-15,000 便宜一半到三分之二。**

但**我们的区域通常比它的整帧更清晰**（region 是 1:1 像素，它的 798×443 是把 1536×864 缩到 0.52x）。

## 四、关键差异：我们不需要看 48 帧

这是最重要的一条。storyboard 是**离线均匀采样**，它必须覆盖整段视频，所以 49 个切点就要 48 张图。

我们是**实时 + 有传感器**：25-60Hz 的信号免费告诉我们「哪里变了」。所以：

- 静态段落 → 0 张图，只用数值（"静止 12 秒"）
- 单次变化 → 1 张 region（169 token）
- 剧烈变化 → 九格（798 token）

**对它来说必须花 10,656 token 的 166 秒，我们可能只需要 1,500-3,000 token 就够回答具体问题。**

## 五、但是 —— 我们有三个硬伤

### ① 视频画面在虚拟屏上冻住【实测】

MediaCodec 输出到虚拟屏 Surface 不刷新：
- GIF 动画（普通 View）：**60fps 完美**
- 视频（MediaCodec）：**26 帧后冻住**

**所以「实时看视频」这条目前不成立。** 除非：
- 找到软解播放器（待验证）
- 或者用主屏 + screenrecord（但那是用户看得见的屏）

### ② 没有音频【实测】

`playback` 抓音我们没接。storyboard 有 ASR，能回答「谁说了什么」。
**这一条它完胜，无争议。**

### ③ 时间成本

166 秒视频我们必须**实时看完 166 秒**才能处理（除非有更快的路）。
storyboard 处理同一段大概 30-60 秒（下载+解码+切点）。

**墙钟时间它赢 3-6 倍。**

## 六、我们能赢的地方（结构性）

| 能力 | 我们 | storyboard |
|---|---|---|
| **能看到正在播的 App** | ✅ | 结构上不能 |
| **能操作（点/滑/输入）** | ✅ | 不能 |
| **闭环验证（做完确认生效）** | ✅ 包数判断，0ms | 不能 |
| **无限流**（不知道什么时候结束） | ✅ | 必须给文件 |
| **DRM/微信/小程序里的内容** | 取决于 FLAG_SECURE（B站实测不拦） | 下载不下来 |
| **单帧清晰度** | region 1:1 = 169 token | 798×443 = 0.52x，222 token |
| **静态段落成本** | 0（传感器免费） | 必须采样 |
| **音频/ASR** | ❌ | ✅ |
| **长视频（>10 分钟）** | ❌ 必须实时看完 | ✅ 离线任意长度 |
| **离线可复现/可审计** | ❌ | ✅ |

## 七、结论：分轨

### Track A｜离线视频理解（给一个文件，问里面有什么）

**我们输，而且不只输一点。**

| 指标 | 我们 | storyboard |
|---|---|---|
| 能处理吗 | ❌ 视频画面冻住 | ✅ |
| 音频 | ❌ | ✅ |
| 墙钟 | 必须实时（166s） | 30-60s |
| token | 1,500-3,000（如果能看到） | 12,000-15,000 |

**token 我们便宜，但前提条件（能看到）不成立。这一轨我们输。**

### Track B｜在线操作与闭环（实时看屏、动手、验证）

**我们独赢，storyboard 结构上不参与。**

| 指标 | 我们 | storyboard |
|---|---|---|
| 能操作 | ✅ | 0 |
| 闭环验证 | ✅ 0ms | 0 |
| 无限流 | ✅ | 0 |
| 实时 | ✅ 60fps 流 | 不适用 |

**这一轨没有对比对象，只有我们。**

## 八、诚实的总结

**「我们比 storyboard 强」这个说法只在 Track B 成立，而 Track B 是它不做的事。**

在它真正擅长的 Track A 上：
- 它 30 秒能读完 2.8 分钟视频，带音频转写，花 12k token
- 我们读不了（画面冻住 + 没音频），就算能读也要实时花 166 秒

**唯一我们能赢 Track A 的方式是「软解能看视频」+「用传感器只挑关键帧」**，
那会让 token 降到 1/5。但第一条还没验证。

## 九、下一步（决定 Track A 能不能翻盘）

1. **验证软解播放器能不能在虚拟屏出画面** —— 这是唯一的关键
2. 如果能：测 166 秒视频用「传感器挑帧」实际花多少 token，和 12k 对比
3. 如果不能：接受 Track A 放弃，把产品定位在 Track B

# 端到端实测：一个真实任务花多少 token

## 任务

在虚拟屏上打开 B站 → 读出首页内容 → 点一个视频卡 → 确认跳转 → 只发一张必要的图。

## 实测（真机，2026-11-16）

| 步骤 | 做法 | 耗时 | 图片 token |
|---|---|---|---|
| 1 | OCR 读首页（30 行，带归一化坐标） | 3327ms | **0** |
| 2 | 点击视频卡 | 732ms | **0** |
| 3 | 验证：`ok=true changed=true probe=video-packets` | — | **0** |
| 4 | 等画面稳定（`waitStable`） | 121ms | **0** |
| 5 | 自动 ROI `{x:179,y:0,w:312,h:312}` area=0.08 | — | **0** |
| 6 | 截一张 region 图 | — | **169** |
| | **合计** | **16.3 秒**（含 6 秒 App 启动） | **169** |

## 这个数字说明什么

**前面五步全部 0 图片 token**：读界面用 OCR、点按用事件注入、验证用视频包数、
等稳用灰度信号、选区域用 bbox+热力图 —— 这些都是我们自己的传感器和算法，
不花一个 vision token。

**只有最后那张 169 token 的局部图是真的花在「看」上的**，而且它是 1:1 像素的 420×420。

## 和 storyboard 的对比

| | 我们 | storyboard |
|---|---|---|
| 能做这个任务吗 | ✅ | ❌ 没有视频文件可下载，B站首页是实时界面 |
| 图片 token | 169 | ≥222/图 |
| 文本 token | OCR 输出的 30 行（约 300-600） | 文本索引另算 |
| 需要先有文件 | 不需要 | 必须 |
| 能操作吗 | ✅ | ❌ |

**在 Track B 上这不是「赢」，是它不参赛。**

## 一个真实的短板：OCR 很慢

3327ms —— 单步占了整轮的 20%。对比点击 732ms、等稳 121ms。

**OCR 是当前感知链路里最慢的一环。** 优化方向：
- 只在需要文字时调 OCR，其余用灰度信号和 region 图
- 或者对固定区域做增量 OCR（只读变化的区域）

## 另一个观察：ROI 这次用了 last-input 兜底

`src: "last-input"` —— 说明当时灰度 bbox 是空的（画面刚稳定、没有变化）。
兜底逻辑生效了，给出了点击位置周围 312×312 的区域，也是合理的。

# 第二轮：成本对账（子代理审计后修正，2026-11-16 晚）

## 三条必须先纠正的自我美化

### ① 整帧单价几乎打平，不能说我们图便宜

| | 尺寸 | token |
|---|---|---|
| 我们整帧 | 544×1203 | **377** |
| 它整帧 | 798×443 | **222** |

**我们整帧比它贵。** 但注意口径：16:9 视频放进 720×1592 竖屏，有效像素只有 720×405，
按 420×236 算才落进地板价 169。算错这一项会让我们的成本虚高一倍。

**任何小于 1.4 倍的差距不能当结论**（计价公式本身有 6% 的不确定度：
798×443 按 `ceil(w/42)*ceil(h/42)` = 209，它报 222）。

### ② 「裁剪便宜」是错的，169 是地板价

| 做法 | token |
|---|---|
| 裁 10 个小角 | 10 × 169 = **1,690** |
| 它一张全帧 | **222** |
| 比值 | 我们贵 **7.6 倍** |

**我们赢在「只需要一个时刻」，不在「裁切便宜」。**
k=2 时 338 > 222，我们反而更贵。

### ③ OCR 不是 0 token

一屏 30 行文字 ≈ 300-600 文本 token，**和一张整帧 222 同量级**。
「OCR 免费」这个说法会被抓 —— 免费的只是**图片** token。

## 一个立刻改进的点（已实施）

token 计价 `ceil(w/42)*ceil(h/42)`，**544 以下全部按地板价 169 收**：

```
420×420 → 169 token，边长 420
544×544 → 169 token，边长 544   ← 同价，边长多 29.5%，面积多 68%
```

**我们原来的默认输出宽度 420 是白扔 30% 分辨率。已改成 544。**

实测效果：

```
T.roi:  region={x:111,y:723,w:544,h:544}  src=sensor-bbox+hotspot  area=0.26
截图:   544×544 = 169 token，放大率 1.00x
全屏对照: 544×1203 = 377 token，放大率 0.72x
```

**便宜 55%，同时清晰 1.4 倍。**

## 八个任务的成本对比

| # | 任务 | 我们 | storyboard | 谁赢 |
|---|---|---|---|---|
| T1 | 读标题文字 | 20-450（0 图片）/1.9-3.3s | 222-444+30/30-60s | 我方（赢延迟 10-20x）|
| T2 | 读数值（血条） | 20 或 169/0.9-3.5s | 222-444/30-60s | 我方 1.3-11x |
| T3 | 理解画面 | 169-230/0.2-0.5s | 444→13,656/30-60s | 我方 1.9-46x |
| T4 | 加载完了吗 | **0**/0.15-0.3s | 444；**活屏不能** | 我方（∞）|
| T5 | 操作+验证 | **0-338**/2-4s | **不可执行** | 我方（分母为 0）|
| T6 | 3 分钟讲了什么 | **不能**（冻帧） | 12,656-14,656/30-60s | **它** |
| T7 | 瞬态事件 | 169/检出 ≤0.02s | 不可行 | 我方（但别吹 436 倍）|
| T8 | 音频台词 | **不能** | 300-500 | **它** |
| — | 单帧问答 | 377 | 222 | 平（6% 误差内）|

## 诚实结论

**赢的 5 个里有 3 个是「它不参赛」，不是「比不过」：**
- T4/T5：它结构上没有闭环
- T7：它是离线批处理，没有「刚才」

**输的 2 个 + 1 个容易漏的：**
- T6：是「看不到」不是「贵」—— MediaCodec 画面冻结
- T8：没有音频
- **离线可复现/可审计它也赢** —— 我们的流转眼即逝，同一问题重问画面已经过去了。
  举证/审计类需求这是硬伤，之前没写进去。

**「能操作」值多少 token**：折算外包一轮 400-600 token + 8-16s，
我们内做 0-338/2-4s，便宜 1.5-3.6 倍。
但**主要价值不是 token，是任务的终止条件** —— 要求状态改变的任务，
操作让成本从 ∞ 变成 ≤338，这是「分母为 0」，不能用倍数描述。

## 对外一句话

> **一个屏幕内、要精确、要动手、要实时 —— 我们赢**（0-338 token，秒级，它多半连参赛资格都没有）。
> **一段 30 秒以上、要听懂台词、要能重放的动态录像 —— 它赢**（13.7k token / 30-60 秒，我们直接做不到）。
> 分界线是「需不需要覆盖时间」和「有没有声音」，不是「谁的图便宜」——
> **整帧单价只差 3.5%，正好落在计价公式 6% 误差里。**

## 两个未验证点（不写进对外材料）

1. **T7 依赖帧环形缓冲**：当前如果只保最新帧，400ms 的 toast 可能抓不到图【待验证】
2. **软解能否在虚拟屏出画面**【待验证】—— 这决定 Track A 能不能翻盘

# 真实跑了一次 storyboard（不是 dryRun）

## 实测参数与产物

```
素材: S3SeasonCG.mp4（166 秒，1536×864，30fps）
窗口: 0-30 秒
策略: auto 选了 full
产物: 12 帧 / 3 张图
画布: 798×443，单格最小 399×222
token: ~726 vision tokens（242/图，约 60/帧）
ASR: 5.8 秒（有音频转写）
切点: 11 个（平均 2.7 秒/镜头）
输出去重: 12 帧里有 8 个是非硬切（6×淡入淡出黑场、1×渐变、1×闪光）
```

## 产物质量

分镜图清楚可读：飞船、穿装甲的女性角色、浮空城市全景、游戏角色特写。
底部有**响度波形**（青色 = 有声，灰色 = 静音，黄色刻度 = 切点）。

**ASR 转写内容**（我们完全拿不到的部分）：
> 「怎么不不理不爱的？ This is more amazing than you described.
> 许 could be here to see it。 You've always dreamed.」

## 五个重要发现

### ① 12 帧只花 726 token —— 比预想便宜

单格 399×222，**每帧约 60 token**。因为它把多帧塞进同一张图，
而图片计价按**画布面积**算，不按帧数。

**这推翻了我之前「48 图 × 222 = 10,656」的算法** —— 那是按「每帧一张图」算的，
实际它会打包，单价降到约 60/帧。

### ② ASR 是硬优势，无争议

台词、语气、说了什么 —— 我们一点都拿不到。这条它完胜，不是「勉强赢」。

### ③ 它的不确定性标注比我们细

同一份输出里主动写：「8 of 11 是非硬切」「6×淡入淡出，1×渐变」「闪光但画面确实变了」
「ASR 是机器转写，技术名词和人名可能听错，引用前先和屏上文字对照」。

**这种自我标注可信度的做法，我们的文档里没有对等的东西。**

### ④ 它自己承认策略不是越大越好

输出里明确写：`"full" is the expensive one, not the fuller one`。
和我之前读它手册时的印象一致。

### ⑤ 30 秒的成本对照（现在有真实数字了）

| | storyboard（实测） | 我们 |
|---|---|---|
| 覆盖 30 秒 | 726 token + ASR 5.8s | **做不到**（视频冻帧） |
| 若能看到 | — | 传感器免费盯 30 秒 + 抓 3 次 region = **507 token** |
| 音频 | ✅ 有台词 | ❌ 无 |

**注意：我们的 507 是假设值（视频能看才行）。实际是 0，因为看不到。**

## 结论更新

**Track A 的差距比之前估的小**（726 vs 假设 507，只差 1.4 倍），
**但「看不到」这个硬伤没变** —— 差 1.4 倍的前提是我们能看，而我们看不到。

**真正拉开差距的是音频**：它能告诉你「说了什么」，我们连画面都停在首帧。
