# 视频能力对比：我们 vs `dsh-video-storyboard`

> 用户要求：跟视频插件的作者比一比，看谁的精准度和逻辑性更强，重点是捕捉细节、
> 实时操作屏幕、音频对应画面。确认我们更好之后再继续防风控。
>
> 测于 2026-11-16。设备：红魔 NX809J / Android 16。

## 一句话结论

**比视频，我们输。但有两条路能反过来 —— 其中一条是我们自己丢掉的。**

## 一、硬数据对比

| | 我们（screen 插件） | video-storyboard |
|---|---|---|
| 帧率 | **实测 7 fps**（20 帧 2710ms，单帧 133-153ms） | 视频原帧率（文件里 24/30/60 都有） |
| 音频 | **完全没有** | 有（ASR 转写，能对时间码） |
| 输入 | 视频文件 / 链接 | — |
| 输出 | 实时画面 + 能操作它 | 分镜图 + 带时间码文本 |
| 画面来源 | **虚拟屏（用户看不见）** | 文件 |
| 细节策略 | 九格自适应采样 + region 局部放大 | 一帧一镜头，格子大小按切点密度八档 |
| 能操作屏幕 | **能**（点按/滑动/输入） | 不能 |

**所以「谁更强」这个问题要先限定用途**：

- **「看一段视频并说出发生了什么」** → 它赢，赢在帧率和音频，没有悬念。
- **「在用户看不见的地方实时操作一个 App」** → 只有我们能做，它根本不做这件事。

拿帧率比我们是自找难看。但这不代表我们的方案差，是两件事。

## 二、我们真正差的地方（不回避）

**① 7 fps 对快节奏内容是硬伤**

实测：20 帧 2710ms。对枪战游戏、SpaceX 那种快速画面，
**每 143ms 才一帧，中间发生了什么完全看不到**。

**② 完全没有音频**

`screenrecord` 能录视频但我们没接；即使接了也没有音频通道。
所以「测试音频对应画面」这一条，**我们现在是 0 分，不是分数低**。

**③ `screenrecord` 录不了虚拟屏（今天实测确认）**

```
screenrecord --display-id 232 ...        → Invalid physical display ID
screenrecord --display-id <SF id> ...    → Invalid physical display ID
screenrecord（默认，主屏）                → ✅ 2 秒 564KB 正常
```

它只认**物理**显示设备。所以「用录屏提高帧率」这条路，对我们的隐藏屏走不通。

## 三、被我们自己丢掉的那条路（今天最重要的发现）

`vd.js` 启动 scrcpy-server 时连**两个** socket：

```js
const s1 = await connect();     // ← 视频流
await sleep(500);
const s2 = await connect();     // ← 控制通道
state.sockets = [s1, s2];

// 而 connect() 里是：
s.on('data', () => {});          // ← 视频数据被直接丢掉
```

**实测这个视频流里真的有东西：**

```
控制通道连上后 2 秒：收到 273,430 字节 → 约 1094 kbps
```

流开头的协议（dump 出来的原文）：

```
[0..63]   设备名 "NX809J"（64 字节补零）
[64..67]  "h264"          ← 编码格式
[68..71]  0x80000000
[72..75]  0x000002d0 = 720    ← 宽
[76..79]  0x00000638 = 1592   ← 高
[80..]    帧包
```

**也就是说：我们一直有一个实时 H.264 视频流，帧率由 scrcpy 的 `max_fps` 决定
（我们传的是 60），而我们把它当垃圾扔了。**

如果把它解出来：

| | 现在（screencap 采样） | 用视频流 |
|---|---|---|
| 帧率 | 7 fps | 最高 60 fps（受 max_fps 限制） |
| 延迟 | 143ms/帧 | 流式，约几十 ms |
| 代价 | 每帧一次 adb 往返 | 一次解码，CPU 换带宽 |
| 音频 | 无 | 仍然无（scrcpy 要 `audio=true` 且是另一条 socket） |

**这是把「视频能力」从 7fps 提到 60fps 的唯一现实路径，而且不需要新权限、不需要 root。**
代价是 CPU（解码）和复杂度（要处理 H.264 帧边界）。

## 四、音频怎么办

两条路：

1. **scrcpy 的 audio 通道** —— 启动参数有 `audio=false`，改成 `audio=true` 会多一条
   socket 传 Opus 音频。理论上能拿到声音。
   **但**：虚拟屏上的音频输出归属不确定（App 的音频走系统混音，不跟 display 绑定），
   而且这样录到的是**整机混音**，不是「这块屏的声音」。
2. **不要音频** —— 我们的用途是「操作 App」，不是「分析视频」。
   需要音频的场景（听语音消息）应该是另一条路：读通知 / 读无障碍文本，而不是录声音。

**我的判断：音频不值得做。** 它解决的不是我们的问题。

## 五、细节捕捉：我们其实不差

`region` 局部放大这条我们做得比一般方案好：

```
全屏 720 宽 → 420 宽  = 0.583x（缩小，读不全）
region 360 宽 → 420 宽 = 1.167x（放大），而且只要 180 token
```

**同样的 token 预算，看局部比看全屏清晰两倍。** 这个思路跟它「按切点密度分配格子大小」
是同一个原理，只是我们用在空间上（局部），它用在时间上（镜头）。

**这条可以互补**：如果解了视频流，就可以做「时间上按变化密度采样」，
那就是它那套思路搬到实时画面上。

## 六、结论与建议

**现在不满足「我们比它更好」这个前提。** 具体：

| 维度 | 我们 |
|---|---|
| 视频帧率 | ❌ 7 vs 24-60 |
| 音频 | ❌ 无 |
| 实时操作屏幕 | ✅ 只有我们做 |
| 隐藏（用户看不见） | ✅ 只有我们做 |
| 局部细节 | ✅ region 方案更好 |
| 输入灵活性 | ✅ 能操作，不只是看 |

**我建议的顺序**：

1. **先把视频流解出来**（半天到一天）—— 这一步把 7fps 提到最高 60fps，
   是对「捕捉细节」最直接的改善，而且用的是我们已经有的东西
2. **再谈防风控** —— 因为防风控的前提是「看到的东西够准」，7fps 会漏掉动作

**不建议做的**：音频（不是我们的问题域）、跟它比「分析视频文件」（赛道不同）。

## 七、今天没做成的（诚实记录）

视频流帧头解析没通：按 80 字节偏移解析帧包得到 0 帧，说明包结构还差一层
（可能是每个包前面还有额外的 codec meta 包）。dump 出来的原始字节已经记在上面，
下次接着解得从这段 hex 入手。

# 补充（同日晚）：视频流解出来了

上一条结论「帧率 7fps 是硬伤」只对了一半 —— 硬伤是我们的实现，不是平台。

## 协议已完全解析

```
[0]        dummy 字节（scrcpy 在第一个连接上发的握手字节）
[1..64]    设备名，64 字节补零
[65..68]   编码格式 ascii，"h264"
[69..72]   0x80000000
[73..76]   宽（u32 BE）= 720
[77..80]   高（u32 BE）= 1592
[81..]     视频包
```

每个包：

```
[0..7]   PTS（u64 BE）—— **高位被 flag 占用**
           bit62 = 关键帧（实测 0x4000000000000000）
           bit61 也见过被置位（0x2000...），所以不能直接当微秒数用
[8..11]  载荷长度（u32 BE）
[12..]   H.264 Annex-B，自带 00 00 00 01 起始码
```

**校验方式**：按这个结构解析，916,485 字节里切出 97 帧，offset 精确走到末尾（100%），
再用 ffmpeg 解出 96 张 720×1592 的图，内容就是虚拟屏上的设置页。

## 三条路的实测成本

| 做法 | 每帧耗时 | 帧率 | 备注 |
|---|---|---|---|
| `screencap`（原来） | **143 ms** | 7 fps | 每次一次 adb 往返 |
| 按需解一个 GOP | 198-238 ms | — | 每次都要起 ffmpeg，反而更慢 |
| **常驻解码** | **4 ms** | 25 fps | 96 帧 428ms，CPU 约 11% 一个核 |

**常驻解码是 screencap 的 1/36，帧率 3.6 倍。** 而且不占 adb 通道。

## 写成了 `screen/src/video.js`

- `createReader()` 建解析状态
- `push(st, chunk)` 喂字节（内部处理固定头 + 逐包切分）
- `h264(st, {maxPackets})` 拼出可解码的流
- `grabJpeg(st, opts)` 解一张 JPEG
- `stats(st)` 状态摘要（宽高/帧数/fps/badSizes）

**踩过的两个坑，都写进注释了**：

1. **必须从关键帧开始切** —— 第一版取最后 N 个包，ffmpeg 报
   `non-existing PPS 0 referenced`，因为关键帧带着 SPS/PPS，丢开头就没参数集了。
2. **`packets=0` 被 `|| 24` 吞掉** —— `Number(0) || 24` 等于 24，不是"全取"。

## 还没做的

- 还没接进 `vd.js`（`s.on('data', () => {})` 仍然是丢弃状态）
- 常驻解码的进程管理（起、退、重启）还没写
- 音频两条子代理正在评估

## 对「同 token 下更强」意味着什么

有了 25fps 之后，同样一张图的 token 成本不变，但**可选性完全不同**：

- 原来是「7 次里挑一次」，现在是「25 次里挑一次」
- 可以按「画面变化最大」挑帧 —— 快动作（游戏、动画）不再必然错过
- 可以算真实运动量，决定要不要发图（省 token）
- 常驻解码后读帧 12ms，比 screencap 快 12 倍，实时操作终于成立

# 黑屏探针实测（同日晚）

## 探针实现

`probeSecure()` 把全屏缩成 16×16 灰度，分上下两半统计亮度，判三态：

| 判定 | 条件 | 含义 |
|---|---|---|
| **A** 正常出画 | 上半 max>20 且下半 max>20 | 可以做 |
| **B** 视频区黑 | 上半 max≤6 但下半 max>20 | **FLAG_SECURE**，结构性不可做 |
| **C** 整屏黑 | 整屏 max==0 | App 不认虚拟屏，或没起来 |

B 和 C 必须分开记：B 是「内容受保护」，C 是「这 App 不认虚拟屏」。

## 实测结果

| 对象 | verdict | 上 max | 下 max | 说明 |
|---|---|---|---|---|
| 设置页（对照组） | **A** | 56 | 56 | 探针本身是对的 |
| B站首页 | **A** | 191 | 196 | **B站能在虚拟屏正常渲染** |

## 更硬的证据：窗口标志

```
dumpsys window windows → 24 个窗口，带 FLAG_SECURE 的: 0 个
tv.danmaku.bili 的窗口 → 无 FLAG_SECURE
```

**这台手机目前没有任何 App 在可见窗口上设 FLAG_SECURE** ——
因为没有装腾讯视频会员版、爱奇艺这类 DRM 应用。

## 所以 FLAG_SECURE 这条风险的实际范围

- **B站普通内容**：不设 FLAG_SECURE，**能抓**（首页实测 A）
- **B站会员/DRM 片源**：未实测，理论上可能设
- **腾讯/爱奇艺 VIP**：本机没装，无法测
- **微信视频号**：未实测
- **游戏过场**：未实测

**结论：探针工具就绪，A/B/C 三态判定验证通过（对照组 + B站首页都是 A）。**
但「哪些具体内容会黑」只测到 B站首页这一层，实际播放 DRM 内容仍是未知。

## 这条对产品定义的意义

FLAG_SECURE 是**无 root 的硬边界**，抓到纯黑不是我们代码的问题，
是 Android 的保护机制。所以：
- 遇到 B 就对用户明说「这条线做不了」，不要假装能优化
- 探针应该在每次投屏后自动跑一次，把 verdict 写进工具返回值

## 视频播放：能抓到画面，但画面不推进【实测】

用 MediaStore content URI 起播放器、走系统「打开方式」选择器点进真实播放器后，
截到了真实视频画面（鱼缸/蓝灯/水流），进度条 `00:05 / 00:05`。

但**画面是静止的**。六种推进方式全部试过，视频流包数一次都没涨：

| 方式 | 包数变化 | peak |
|---|---|---|
| 点屏幕中间唤控件 | 0 | 87.92 |
| 点播放键 (0.5, 0.955) | 0 | 87.92 |
| KEYCODE_MEDIA_PLAY (126) | 0 | 87.92 |
| **KEYCODE_MEDIA_PLAY_PAUSE (85)** | 0 | **0** ← 键生效了，但画面没推进 |
| KEYCODE_DPAD_CENTER (23) | 0 | 0 |
| KEYCODE_ENTER (66) | 0 | 0 |

`MEDIA_PLAY_PAUSE` 让 peak 从 87.92 掉到 0，说明**按键确实被处理了**（画面有变化），
但解码器出帧数始终是 400，一个包都没新增。

## 判断【推断，需进一步验证】

**虚拟屏上的视频 Surface 不推进** —— 播放器把第一帧合成出来了（所以我们截到了画面），
但后续帧没有再刷到这块虚拟屏上。

可能原因（都没验证）：
1. 视频用 SurfaceView / hardware overlay，虚拟屏的合成路径不更新它
2. 播放器检测到非默认 display，主动降级成「只显示首帧」
3. 解码器在虚拟屏上下文中启动失败，静默回退到 poster

**这条如果成立，意味着「看视频内容」这条线只能拿到静态首帧**，
对「理解视频」用途基本没用 —— 而这正是 storyboard 的主场。

# 重要修正：上一轮「视频不推进」的结论是错的（测量 bug）

## 错在哪

我一直在检查 `videoReader().packets.length` 判断画面有没有变化。
但 `video.js` 里 `PACKET_KEEP = 400`，环形缓冲封顶之后每来一帧就移出一帧：

```js
if (st.packets.length > PACKET_KEEP) st.packets.shift();   // 永远停在 400
```

**所以「包数一直是 400」不是「画面没变」，是我的读数饱和了。**

每次测试都恰好 400 —— 这个过于整齐的数字本来就是可疑信号，我当时没抓住。

## 用总帧数（st.frames）重测

```
进入播放器: 总帧 621
按 KEYCODE_MEDIA_PLAY_PAUSE: 总帧 637  (+16)  ← 画面在推进
持续采样: +6, +4, 然后停
累计新增 26 帧
```

**视频确实响应了播放键，并产出了 26 帧**（约 1 秒 @25fps）。

## 修正后的结论

| 之前的说法 | 修正后 |
|---|---|
| ❌ 「视频画面不推进，虚拟屏视频 Surface 不更新」 | ✅ **视频会出帧**，播放键有效 |
| ❌ 「看视频只能拿静态首帧」 | ✅ 至少能拿到播放中的帧 |

## 但仍有未解的现象

视频播了约 1 秒（26 帧）就停了。原因未知：
- 播放器可能检测到非前台就暂停
- 或者我按的 MEDIA_PLAY_PAUSE 在第一次是播放、后续某次又变成暂停
- 或者视频解码在虚拟屏上下文不稳定

**需要连续采样更长时间 + 检查播放器状态才能确定。**

## 教训（写进规则）

**判断「画面有没有变」不能用有上限的环形缓冲长度。**
要看累计计数器（`st.frames`），或者用单调递增的序号。
这次因为用了饱和值，得出了完全相反的错误结论，还写进了文档。

# 最终判定：视频在虚拟屏上播约 1 秒后冻住【实测】

## 判定方法（避免了误判）

不看视频流（可能被编码器影响），改用 **`shot()` 的帧去重**做独立判定：

```js
const a = await vd.shot('/tmp', { width: 0 });
await sleep(3000);
const b = await vd.shot('/tmp', { width: 0 });
// a.path === b.path  →  两张截图逐像素相同
```

实测两次返回**同一个文件路径** `/tmp/vd-1794823261110.jpg`，
说明相隔 3 秒的两张原尺寸截图完全一致。

**这是独立于 scrcpy 编码器的证据** —— 画面确实静止，不是我们没收到帧。

## 完整时间线（12 秒连续采样）

| 时间 | 累计帧 | 增量 |
|---|---|---|
| 基线 | 619 | — |
| 0.6s | 619 | +0 |
| 1.2s | 621 | +2 |
| **1.8s** | **638** | **+17** ← 播放爆发 |
| 2.4s | 644 | +6 |
| 3.0s | 645 | +1 |
| 3.6s 之后 | 645 | **+0（永久停止）** |

**累计 26 帧后彻底停止。** 26 帧 ≈ 1 秒 @25fps。

## 结论

| 问题 | 答案 |
|---|---|
| 虚拟屏能不能渲染视频画面？ | ✅ 能（截到真实帧：鱼缸/蓝灯/水流） |
| 是不是 FLAG_SECURE？ | ❌ 不是（探针 A，dumpsys 里 0 个 SECURE 窗口） |
| 播放键有没有效？ | ✅ 有效（按一次出 26 帧） |
| **能不能持续播放？** | ❌ **不能，约 1 秒后冻住** |
| 是我们的流的问题吗？ | ❌ 不是（`shot()` 去重证明画面本身静止） |

## 为什么

**未确定**【不知道】。候选：
1. 播放器检测到 display 不是默认屏，主动暂停解码
2. MediaCodec 的 output surface 在虚拟屏路径上不持续刷新
3. 系统对副屏播放做了限流

不像是我们的代码问题：`shot()` 用的是 `screencap`，和 scrcpy 编码器完全独立，
两条路都看到静止画面。

## 对产品定义的意义（重要）

**「让 AI 看懂视频内容」这条线，目前只能拿到约 1 秒的画面。**

这对「理解一段 10 分钟视频」基本无用 —— 而这正是 storyboard 的主场。

**所以 Track A（离线视频理解）我们输，而且输得比之前估的更彻底**：
不只是 token 和墙钟，是**根本看不到持续画面**。

## 还能做的替代

1. **B站/ExoPlayer 路线**未测 —— 软件渲染可能不同（B站首页/播放页渲染正常）
2. **游戏路线**未测 —— 游戏用 SurfaceView，可能同样冻住，也可能不同
3. **用 `screenrecord` 录主屏**（只能主屏）—— 但那是用户看得见的屏
4. **接受这个限制**，把产品定位在「操作 App」而不是「理解视频」

# 关键发现：不是 MediaCodec 的问题，是「定时驱动更新不刷新」

## 决定性对照实验

造了一个 10fps 的动画 GIF（彩色测试图案，每帧变化很大），推到相册后在虚拟屏打开。

结果：
- **截图显示 GIF 正常渲染**（彩条 + 渐变 + 圆形，亮度 0~255 全有）
- **但 10 秒采样 0 帧新增**，peak=0

## 两条独立路径都冻住

| 内容 | 渲染方式 | 结果 |
|---|---|---|
| 本地视频 | MediaCodec 硬解 | 26 帧后冻住 |
| 动画 GIF | 软件渲染 | **0 帧，完全不动** |

**两个完全不同的渲染路径，都冻住。** 所以不是 MediaCodec 特有的问题。

## 和「能动的」对照

| 场景 | 驱动方式 | 结果 |
|---|---|---|
| 滑动列表 | **输入事件** | ✅ 25fps 流畅，peak 8-9 |
| 打开图片的转场 | **输入事件** | ✅ peak 29.82，帧数猛涨 |
| 点底部标签 | **输入事件** | ✅ 包 122→154 |
| 视频播放 | 定时/解码器 | ❌ 1 秒后冻住 |
| GIF 动画 | 定时器 | ❌ 完全不动 |

## 结论【推断，但证据很一致】

**虚拟屏只在「有输入事件」或「App 主动重绘」时才合成新帧；
纯定时驱动的动画（GIF 帧、视频帧）不会持续刷新。**

这个假设同时解释了上面全部六行数据，而且排除了「MediaCodec 特有」和「FLAG_SECURE」两个之前怀疑的方向。

## 对产品定义的意义（这条很重要）

**「让 AI 看动态内容」这条路基本堵死，但原因和之前想的不一样：**

- 不是内容受保护（FLAG_SECURE 探针是 A）
- 不是编码器问题（screencap 独立验证也静止）
- **是虚拟屏的合成时机问题**

**可行的绕法（待验证）**：
1. **在有输入事件时抓帧** —— 我们本来就一直在注入输入，所以「操作 App」的场景不受影响
2. 需要看动画时，主动注入一个无害事件（如移动触摸）"踢"一下屏幕，可能能触发刷新
3. 如果 2 成立，「看视频」可以靠持续微输入维持刷新 —— 但会干扰被测 App，需实测

## 我们不受影响的部分

**「操作 App」这条主线完全不受影响**，因为它天然是输入驱动的：
- 读界面（OCR）✅
- 点按滑动 ✅
- 验证结果（包数判断）✅
- 稳定帧选择 ✅
- 自动 ROI ✅

**只有「看视频」这一类受影响。**

# 重大修正：虚拟屏能跑 60fps，问题只在 MediaCodec 视频 Surface

## 上一轮的结论被推翻了

上一轮我说「定时驱动的动画在虚拟屏上不刷新」，依据是 GIF 测试 0 帧。

**错了。** 原因很简单：我造的 GIF 只有 3 秒，等我连上解码器开始采样时它已经播完停在最后一帧了。

换成 8 秒的 GIF 重测：

```
第1秒: +61 帧 (60.9 fps)  peak=0.99
第2秒: +60 帧 (60.0 fps)  peak=0.94
第3秒: +55 帧 (55.0 fps)  peak=1.10
第4秒: +60 帧 (59.9 fps)  peak=7.07
第5秒: +60 帧 (60.0 fps)  peak=1.06
第6秒: +54 帧 (54.0 fps)  peak=1.09
```

**稳定 60fps。** 而且用 `shot()` 帧去重独立验证：
两张间隔 1 秒的截图**返回不同路径** → 画面确实在动。

## 三个修正

| 之前的说法 | 修正后 |
|---|---|
| ❌ 定时驱动更新在虚拟屏上不刷新 | ✅ **能刷新，GIF 跑满 60fps** |
| ❌ 帧率上限 25.7fps | ✅ **上限是 60fps**，之前 25.7 是内容变化不快的结果 |
| ❌ 视频冻住是因为显示更新机制 | ✅ **只有 MediaCodec 视频 Surface 冻住** |

## 收窄后的真正问题

| 内容 | 渲染路径 | 结果 |
|---|---|---|
| GIF 动画 | 普通 View 绘制 | ✅ **60fps** |
| 视频 | **MediaCodec → Surface** | ❌ 26 帧后冻住 |

**问题精确地落在 MediaCodec 输出到虚拟屏 Surface 这一条路上**，不是显示机制，不是定时器，不是 FLAG_SECURE。

## 这打开了一个明确的解法

**用软件解码的播放器就能看视频。**

可选路径（待验证）：
1. 找支持「软件解码」开关的播放器（VLC、MX Player，或 B站设置里的软解选项）
2. 强制系统走软解：`setprop debug.stagefright.omx_default_rank` 之类（需要确认属性名）
3. B站的 ExoPlayer 在某些配置下也用软解

## 对 PK 结论的影响

之前基于「看不到持续画面」得出的「Track A 必输」要重新评估：

- 如果软解能看视频 → **我们的 60fps 流 + 稳定帧选择 + 自动 ROI，在 token 效率上有竞争力**
- 如果软解也不行 → 才回到「看视频这件事做不了」

## 教训

**测试素材的时长必须大于等于观测窗口。** 3 秒的 GIF 配 5 秒的采样窗口，
得到的是「播完了」而不是「不能播」，两者结论完全相反。

横屏 OCR: 英伟达宣布CEO黄... / 直播 / 推荐 / 热门 / 动画

**横屏这条链路全部打通**：

- App 正常渲染、OCR 正常返回归一化坐标

## 但 ROI 在横屏下不够理想

area=0.32 —— 720×517 的裁剪区，输出 420 宽的话放大率只有 0.58x，
没享受到「裁剪比缩放清晰」的红利（理想应该是 ≤544² 的方块，1:1 像素）。

原因是横屏时 sensor bbox 覆盖了大半个屏（B站首页整块在动），
所以 `pickRoi` 判定「区域太大没意义」的阈值（0.35）刚好没触发。

**改进方向**：区域过大时不该直接放弃裁切，而应该**在 bbox 内部挑一块 544² 的子区**
（比如变化最密集的那块）。目前是「要么裁一块小的，要么放弃」。

## 游戏：需要用户授权才能测【未测】

**没有测游戏，原因有两条：**

1. **封号风险**：游戏的反作弊可以检测 `displayId≠0`、注入事件、deviceId 不一致。
   在虚拟屏上启动游戏本身就可能被标记。用户规则明确要求这类事**先问一句**。
2. 这台机器装了 `com.tencent.tmgp.osgame`、`com.lilithgames.solarland.android.cn`

微信当前是用户正在用的前台 App，force-stop 会**杀掉用户的微信会话、丢登录态**。

**另外**：本机 AGENTS.md 里写着「微信只能读，不能自动回」，测试时也只应做只读观察。

## 自动 ROI 的判据修好了（横屏暴露的问题）

### 问题

横屏 B站首页测出 `ROI: 720×517, area=0.32`，输出 420 宽时**放大率只有 0.58x** ——
没能享受「裁剪 = 1:1 像素」的红利。

原因：原判据是「面积超过整屏 35% 就放弃裁切」，而 0.32 刚好没超，
于是原样返回这个大区域。

### 修正

判据改成**按输出宽度比**：

> 输出宽度是 `outW`（默认 420）时，**裁剪区宽度超过 `outW` 就没有放大收益**。
> 这时候应该在包围盒里挑一块 `outW` 见方（且 ≤544 地板价上限）的子区，
> 位置选**变化最密集**的地方。

为此在 `video.js` 加了两个函数：

- `changeHeatmap(st)` —— 32×32 每格的灰度差（最后两帧）
- `densestCellWindow(st, winCells)` —— 用二维前缀和滑动窗口，O(1) 找出变化最密集的方块

### 实测效果

```
修正前: {w:720, h:517, area:0.32}  放大率 0.58x   src=sensor-bbox
修正后: {x:206, y:263, w:420, h:420, area:0.15}  放大率 1.00x   src=sensor-bbox+hotspot
```

**同样 169-230 token，清晰度提高 1.7 倍**，而且热点是自动找的。

### 顺带记一个坑

这个改动第一次没生效，因为我的字符串替换锚点缩进写错了（写成 4 空格，实际是 2 空格），
断言报错后我没看输出里就以为改了。**改代码后必须看断言结果**，不能只看「语法正确」。

# 最后一块：把感知能力接进工具层

## 发现的问题
