# 性能审计：2 秒/步里 30ms 在干活，1970ms 在确认「屏还活着」

> 审计日期 2026-11-17。只读代码分析，未连设备。**下面的数字多数是估算，需要实测确认**，
> 已逐条标注。

## 三个反直觉的发现

### 发现 1：`vdisplay_input` 慢不是注入慢，是每步先跑 5 次 dumpsys

调用链（代码位置）：

```
vdisplay_input → vd.input()
  ↓ vd.js:1331  await start()          ← 每次 input 都先确认屏
     ↓ 屏已存在走复用分支 vd.js:289-313
        · alive()  → displayIds + sfIds 两次 shell
        · dumpsys display | grep
        · getprop
  ↓ vd.js:1345  refreshRealSize()      ← 又一次 dumpsys window displays
  ↓ vd.js:1549  sleep(settleMs||500)   ← 固定等 500ms
  ↓ vd.js:1414  tap 内部 8-22ms 拟人化间隔
```

**共 5 次 adb shell 往返。** `dumpsys display` 和 `SurfaceFlinger --display-id` 是最重的两条。
按 150-300ms/次估 → 0.75-1.5s【估算，未实测】。

加固定 500ms 和拟人化间隔 = **1.3-2.1s**，正好对上实测的 2 秒。

**真正的 socket 往返 <1ms；真正注入本身 <10ms。**

> 2 秒里 **30ms 在干活，1970ms 在确认「屏还活着、屏多宽」**。

### 发现 2：OCR 的 1.6-3.3s 花在逐框 rec，不在检测

`det_limit_side_len=320` 已把检测压到 320×707（约 0.1-0.2s）。
剩下是 **96 个框 × rec（batch 6 → 16 批）+ use_cls 对 96 框各跑一次角度分类**。

**框数 96→8，rec 直接掉 85%。**

### 发现 3：多屏并行被一把全局锁堵死

`vdisplayd.mjs:255-280` 的 `MUTATING` 集合含 `input/shot/launch/text`，
全排在同一条 `mutexTail` 上。

**A 屏做 1.6s OCR 时，B/C 屏的点击在排队。**

`pool.js`/`lease.js`/`occupancy.js` 在**调度层**并行，**执行层**串行。
所以「3 个 AI 同时操作 3 个 App 提速 3 倍」现在做不到。

## 准确性：包数变化是「好触发器、坏证据」

**失效场景**：
- 画面本来就在动（B站视频 / 秒表 / 轮播）→ 永远 `changed:true`，**校验等于被关掉**
- 屏进 doze → 永远 false
- displayId 不匹配时 scrcpy 服务端**静默丢弃**（`inject.js:66` 注释已写）

**正确做法是四层证据**：

| 层 | 手段 | 成本 | 证明什么 |
|---|---|---|---|
| L0 | 视频包数 | 0ms | 画面在变 |
| L1 | 区域哈希 | 10ms | 变的是我关心的区域 |
| L2 | `dumpsys input` RecentQueue | 50-100ms | **事件送到了窗口** |
| L3 | **无障碍事件流** | ~0ms | **被 View 消费了**（还能抓 Toast）|
| L4 | 语义断言 | OCR | 结果符合预期 |

**「没生效 vs 生效了但画面没变」** 用 L2 × L3 × 画面三个正交通道就能分开：

- 送到了 + 被消费 + 画面没变 = **无视觉变化的成功**（开关/聚焦）→ **不要重试**
- 送到了 + 没被消费 = 坐标偏 / 不可点
- 没送到 = 通道坏

现在那 17.6% 白点大部分混在后两种，**处置相反却共用一个 `changed` 字段**，
所以只能盲重试，**重试又制造连点特征**。

> **这是准确性问题的真根源，不是坐标精度。**

## 传感器判据：全局 MAD 会漏检小区域

现在 `sampling.js:41` 的 `DIFF_KEEP = 0.005` 是**全屏平均**。

算例：100×40 的「关注→已关注」按钮，只覆盖 4 格（22.5×49.75px/格），
灰阶差 80 → **全局 MAD = 0.0012 漏检**，`maxCell = 0.31` 稳稳检出。

**改法**：`maxCell > 0.15 || mad > 0.005`

## 和市面比

- **UI-TARS-1.5**（字节，AndroidWorld 46.6）明确「仅截图、不用无障碍树/DOM」
- **AutoGLM**（智谱，2025-12 开源，9B）VLM 看屏 + ADB
- **Mobile-Agent-v3 / GUI-Owl**（AndroidWorld 73.3）端到端多模态
- 大模型派都视觉优先；基础设施派（uiautomator2 / mobile-mcp / Android-MCP）才用无障碍树

**「60Hz 不独有」**：游戏机器人圈子 minitouch/maatouch 早就高频注入（MAA/ASL 在用）。
LLM Agent 圈子里确实没有（全是 1-3s 离散 tap）。

准确说法：架构同 Cradle(2024, PC 游戏) 的「高层规划 + 低层闭环」，
**在 Android + 无 root + 隐藏虚拟屏这个组合没找到同样实现**，
但只检索一轮，标【不知道】，**别当结论对外说**。

**会不会重复造轮子**：agent 循环那层最挤（全开源），别在那创新；
建屏/编码/注入已是 scrcpy；无障碍树别从零设计。
**唯一没人做的是「后台虚拟屏 + 可并行 + 60Hz」三者同时成立。**

## 最高价值且唯一未被证伪的假设

**app_process + UiAutomation 读无障碍树**（1.6s → 0.05-0.1s，且准确率质变）。

**先花 1 小时做可行性实验再决定**：写最小 `app_process`，反射拿 `UiAutomation`，
打印 `getWindows()` 每条的 `getDisplayId()`，**只看有没有那块虚拟屏**。

- 有 → 感知层重写，收益 20 倍
- 没有 → 永久关闭，写进 `LIMITS.md` 的 A 类
