# 风控等级的生命周期：操作中触发怎么办、定高了怎么降、定低了怎么升

> 只读源码得出。每条标【实测】（文件:行号）/【推断】/【不知道】。
> 审查对象：`docs/risk.json`、`docs/OPERATION-PLAYBOOK.md`、`docs/AI-使用手册.md` §5、
> `screen/src/tools.js`、`screen/src/vd.js`、`overlay/src/com/dsh/overlay/OverlayService.java`、
> `framesrv/src/com/dsh/framesrv/Main.java`、`docs/产品意图.md`。

---

## 0. 一句话结论

**现在的「定级」不是一个机制，是一次性的文字记录。** 等级写进内存里一个对象、再抄一份到设备上的一个文件，浮窗读它显示颜色；**没有任何代码拿它去拦操作、去数次数、去判断能不能变**。所以要回答用户的三个场景，缺的不是策略，是三层基础设施：

1. **闸门（Gate）**——等级+行动+禁止清单参与每次注入前的放行判断；
2. **账本（Ledger）**——按 `display×包×会话` 记录「定过级、触发过几次风控、试过什么」；
3. **探测器（Probe）**——不需要 AI 主动看，注入后自动取一帧查风控信号。

## 2. 第一层：目前根本没有「发现」风控的能力

要设计「操作中触发怎么办」，先把「发现」这条路摸清。现有可用信号按**可靠性从高到低**排：

### 2.1 检测手段可靠性排序（这是本设计的地基）

| 级别 | 信号 | 怎么拿 | 误报/漏报 | 依据 |
|---|---|---|---|---|
| **S0 最可靠** | **用户说停**（点浮窗 ✕ / 划掉浮窗 / 拖到滑轨右端删除） | `events.log` 新行 `type=user_deleted`、`stopScreen=1`；或 `stop-request` 文件出现 | 几乎零误报（只有用户主动点）；漏报=用户没点 | 【实测】`framesrv/Main.java:1033-1050`、`tools.js:2977-3021` |
| **S1 高** | **当前是系统窗口**：输入拦截层、验证码 WebView、风险提示对话框 | `dumpsys window` 里 `mCurrentFocus` 的 `package/activity` **不属于目标包**（是 `com.android.*`、`com.tencent.*` 的 `...webview...`/`Auth...`、`com.google.android.webview`），且是一层覆盖窗口 | 误报低（登录页、广告页也会命中）；**漏报高**（App 自绘的验证码在同一个 Activity 里，不换窗口） | 【推断】依据：本机没有现成实现，`dumpsys window` 已在 `vd.status` 里用了 |
| **S2 中高** | **App 自己整页弹出的风险页**：Activity 名命中黑名单（含 `Captcha`/`Verify`/`Risk`/`AuthWebView`/`Security` 等） | `dumpsys` 的 `mFocusedApp` 里 activity 段 | 误报取决于黑名单（普通「设置」页若叫 `SecuritySettings` 会误报）；漏报同 S1 | 【推断】 |
| **S3 中** | **文本模式**：OCR 命中「验证码/滑块/拖动滑块/请完成安全验证/账号异常/设备异常/操作频繁/环境异常/请稍后再试/为了你的账号安全」 | `vdisplay_text` 或 `ocr.recognize` | **误报中等偏高**（聊天、搜索用词库、教程页面都会出现这些词——微信里「验证码」三个字一天出现好几次）；**漏报高**（画中画、WebView 自绘、低对比、小字） | 【推断】未做真机误报率测量，**不要引用具体比例** |
| **S4 中低** | **画面模式**：滑块条（横条 + 深色缺口）/ 图形点选 / 九宫格 | 模板匹配/颜色检测（`find_image`、`find_color`，5–30ms） | 需要每个 App 单独做模板；**模板是 App 版本相关的，会过期** | 【推断】工具能力有（`tools.js:2420-2472`、`:2656-2698`），模板不存在 |
| **S5 低（事实来源）** | **系统通知**：App 自己发的「账号异常，请重新登录」 | `dumpsys notification --noredact` | 与浮窗页面无关（可能来自另一台设备/另一时段），**不能当实时证据**，只能当「事后发现」 | 【实测】`OPERATION-PLAYBOOK.md:173` 已把它当只读手段列出 |
| **S6 最低** | **限流/变慢/按钮不响应** | 连续 N 次 `input` 后画面 `changed:false` 或转圈 | 噪音极大（网络慢、转场慢都会这样） | 【推断】 |

**结论（这条决定了整个设计）：**

- **插件能自动检测的只有 S0/S1/S2，其它一律靠 AI 或用户。**
- **S3/S4 只在「显式开启风控探测」时用**，且必须做到「命中→停」，不是「命中→记一笔」。
- **绝对不能只靠 AI 自己看**：`input()` 默认不截图（第 11 条），85 次操作没有一次看画面的案例已经证明。AI「看画面」只在它主动调 `vdisplay_shot`/`vdisplay_text` 时才发生，而风控弹窗恰好出现在两个工具调用之间。

### 2.2 探测器放在哪：三个位置，按成本排

```
位置 A：input() 内部（同步、闸门）
  · 只做 S0/S1/S2（一次 dumpsys，约 250ms；input 本身 100-300ms）
  · 命中 → 返回值不是「已注入」而是「已拦截 + 原因 + 下一步」
  · 不能做 OCR（2-3 秒会把每次点击拖慢 10 倍）

位置 B：input() 返回前（异步、不阻塞）
  · 注入后 400ms 取一帧小图（width 240，约 130ms），交给 OCR 进程
  · 记录命中结果，下一次 input() 进入闸门时读到
  · 代价：多一次截图 + 一次 OCR 排队，不影响 AI 这一轮的等待

位置 C：独立探测循环（后台、每 N 秒）
  · daemon 每 10 秒 tick 里加一步（`vdisplayd.mjs:898` 已有风控同步的位置）
  · 只在「最近 30 秒内有注入」时跑，避免空闲时白烧 OCR
  · 唯一能覆盖「风控弹窗在 AI 停手后才出现」的场景
```

**【推断】推荐：A + C。** A 是硬要求的兜底（用户说的「定级后才允许操作」只有在 A 上才成立）；C 是「操作中触发」的真正答案——**风控常常不是在你点的那一下弹出来的，是几秒后**。B 的价值在 A+C 之间是冗余的，可以先不做。

## 3. 场景一：操作中触发风控

### 3.1 状态机

```
                 ┌────────────────────────────────────────────┐
                 │           RUNNING（正常执行任务）            │
                 └───────┬──────────────┬──────────────┬──────┘
        S0 用户说停      │   S1/S3/S4   │   S2 换Activity│
                         │   命中         │   且页面像风险页 │
                         ▼                ▼               ▼
              ┌──────────────┐   ┌─────────────────────────────────┐
              │  SUSPENDED   │   │        SUSPECT（可疑）            │
              │  用户叫停     │   │  · 仅暂停当前这条动作路径         │
              │  等用户确认    │   │  · 不做任何注入，返回「停下自查」  │
              └──────┬───────┘   │  · 要求 AI 截图确认（一次）        │
                     │            └───────┬──────────────────┬─────┘
     用户说继续       │              AI 确认是风控        AI 确认是误报
                     │                    │                  │
                     ▼                    ▼                  ▼
              ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
              │  RUNNING     │   │  TRIPPED #1  │   │  RUNNING      │
              │  等级不变     │   │  记录一次     │   │  同一包同一屏  │
              └──────────────┘   │  强制 ≥L3     │   │  该信号 24h 内 │
                                 │  锁写操作     │   │  再出现视为真  │
                                 └──────┬───────┘   └──────────────┘
                                        │ 用户/AI 处理完（人工过验证码）
                                        ▼
                                 ┌──────────────┐
                                 │  CHECKED     │  用户说「过了，继续」
                                 │  仍 ≥L3       │  → 只能读、写需用户逐次批准
                                 └──────┬───────┘
                                        │ 同一包再次触发
                                        ▼
                                 ┌──────────────┐
                                 │  TRIPPED #2  │  写到设备账本 + 宿主账本
                                 │  全停          │  critical 边 + 浮窗「已停」
                                 │  交给人        │  工具返回拒绝对该包的一切注入
                                 └──────┬───────┘
                                        │ 用户明确「解除」
                                        ▼
                                 ┌──────────────┐
                                 │  LOCKED      │  等级只能由用户改，AI 不能
                                 └──────────────┘
```

### 3.2 每个决策点的判据

| 状态 | 进入判据 | 动作（必须有实现） | 退出判据 |
|---|---|---|---|
| RUNNING | — | 正常注入 | 命中任一信号 |
| SUSPENDED | `events.log` 有新 `user_deleted` 或 `stop-request` 出现 | 拒绝一切注入，返回「用户叫停了，先问用户」；`vdisplay_edge critical` 或让浮窗显示「已停」 | 用户回话 |
| SUSPECT | S1/S2 命中（焦点跳到了非目标包的窗口，且像验证页） | **只拒绝一次**，返回「可能触发了风控，请先 `vdisplay_shot` 确认」+ 这一帧的截图路径（省 AI 一次往返） | AI 说误报 → RUNNING（记 1 次误报）；AI 说真的 → TRIPPED #1 |
| TRIPPED #1 | S1/S2/S3/S4 任一**确认**命中 | ① 账本写一条；② 有效等级提到 `max(当前, L3)`；③ 写操作一律拒绝，直到用户批准；④ 浮窗 `critical`；⑤ 通知用户 | 用户处理完并说「继续」→ CHECKED |
| CHECKED | 用户明确说「验证过了/继续」 | 仍 ≥L3；写操作每次都要用户批准（不是一次批准管全程） | 同包再触发 → TRIPPED #2 |
| TRIPPED #2 | 同一包 `tippedCount ≥ 2`（**跨会话**） | ① 全停：拒绝该包一切注入（包括读操作里的点击）；② 浮窗「已停·交给人」；③ 工具返回值写明「这条包已停止操作，需你本人解除」 | 用户明确说「解除」→ LOCKED |
| LOCKED | 用户解除后 | 等级只接受用户口述值；AI 调 `vdisplay_risk` 降级一律被拒 | 用户改口 |

### 3.3 「第二次触发」怎么数——这是本节最关键的实现问题

**要回答四个问题：存在哪、跨会话吗、怎么算同一个目标、怎么重置。**

#### (a) 存在哪：三层，各有职责

```
① 设备层（真源，浮窗和 daemon 都读得到）
   /data/local/tmp/dshframe/risk.ledger
   一行一条，追加写，不覆盖：
     ts|pkg|displayId|signal|evidence|sessionId
   例：
     1795800000123|com.xunmeng.pinduoduo|1333|S3|captcha_text|s-7f3a
     1795800500999|com.xunmeng.pinduoduo|1333|S3|captcha_text|s-7f3a
   · 为什么放这里：和 opmode / edge / events.log 同一个目录，同一种写法（原子写 tmp+mv，vd.js:2666-2671 已有先例）
   · 任何进程（daemon、插件、浮窗）都能读；真机重启不清（/data/local/tmp 是持久分区）【推断：Android 12+ /data/local/tmp 在重启后保留；没有在本机验证过】
   · 保留策略：按包只保留最近 20 条 / 90 天

② 宿主层（AI 换会话也能看到）
   $DSH_HOME/plugin-screen/risk-ledger.json
   { "com.xunmeng.pinduoduo": { tippedCount: 2, lastTripAt: 1795800500999,
                                sessions: ["s-7f3a","s-9c11"], state: "LOCKED" } }
   · 为什么需要：风险等级本身没持久化（用户已知的问题），账本必须先持久化，否则「跨会话」无从谈起
   · 已有同目录先例：user-events-seen.txt（tools.js:2994）

③ 进程内缓存
   _riskLedgerCache = { pkg -> {...} }，5 秒过期，避免每次 input 都 cat 设备文件
```

**【实测前提】** 浮窗是普通 App（untrusted_app），`/data/local/tmp` 是 shell_data_file —— 浮窗自己写不了（`framesrv/Main.java:1057-1060` 有现成注解）。所以**账本由 Node 侧（shell 域）写，浮窗只读**；浮窗要显示「已停」，走 `opmode` 那一行（Node 写、浮窗读），不要指望浮窗写账本。

#### (b) 什么算「同一个目标」

用户原话是「同一目标第二次触发」。目标 = **包 × 账号级别**，但插件看不到账号。所以：

- **同一个目标 = 同一个 `pkg`**（最保守、可实现）；
- **不同 displayId 算同一个目标**（同一个包在两块屏上，风控也是同一个账号）；
- **「目标」不区分页面**：在首页触发和在订单页触发都算同一个包。

#### (c) 计数怎么算

```
tippedCount(pkg) = 过去 24 小时内、不同 sessionId 的 TRIP 次数（去重）
```

- **按 sessionId 去重是防刷的关键**：同一个会话里连命 10 次（比如验证码页一直挂着，每次注入都命中 S3）**只算 1 次**。否则 AI 每点一下都「触发」，第二次就全停了，用户明明什么都没做。
- 跨会话再命中，`tippedCount = 2` → 停。
- **同一会话内第二次命中**：仍然停（用户原话是「第二次触发就停止操作，告诉他」——`AGENTS.md` 【风控与操作方式】一节）。但账本里写 `tippedCount=2, sameSession=true`，浮窗显示「已停（你刚才试过一次）」——让用户知道这不是新问题。
- 取 24 小时而不是「永久」：风控冻结通常按天解。**这是推断，不是实测**；依据是常见 App 的「账号异常 24 小时」提示，本机没验证过。

#### (d) 重置条件

| 触发 | 效果 | 谁触发 |
|---|---|---|
| 用户明确说「已经处理好了」 | `state: LOCKED → CHECKED`，计数归零，但保留 `everTripped: true` | 用户口述，AI 传给 `vdisplay_risk` 的 `userSaid` 字段（新增参数） |
| 过了 24 小时且用户再没触发 | 计数按时间窗自然回落 | 时间 |
| App 卸载重装 / 账号切换 | **不重置**（同一台设备、同一账号，风险不降） | — |
| daemon 重启 / 插件重载 | **不重置**（账本在文件里） | — |

**不要给 AI 一个「清零计数」的工具**：它为了继续操作会去调。计数只能由用户动作或时间窗改。

### 3.4 发现后怎么处置——优先级和边界

**「停」的定义要拆开，否则会和「用户要它干活」冲突：**

| 处置 | 何时用 | 具体 |
|---|---|---|
| **停注入，继续观察** | 只命中 S1/S2（可疑） | 拒绝注入；允许 `vdisplay_shot`/`vdisplay_text`（AI 要看图确认）；不允许 `vdisplay_launch` |
| **停整个包** | TRIPPED #1 | 该包一切注入拒绝；其它包不受影响（多 App 场景要留活路） |
| **停整个屏** | TRIPPED #2 / 用户说停 | `vdisplay_stop` 或至少让该屏所有工具返回拒绝；`stop-request` 文件已有一条类似机制（`vd.js:1408-1412`）|
| **交给人** | TRIPPED #2 / L4 包的任何写 | 返回文本给出：截图路径、当前页面标题、可以点的按钮，**让用户自己在主屏处理** |

**为什么不停「整个 daemon」**：`产品意图.md` 的核心是「AI 在另一块屏干活，用户看得到」。停整个 daemon 等于把用户的另一块屏也弄没了。**停的是这个包、这块屏，不是这个服务。**

### 3.5 浮窗上怎么显示（含现在的两个缺陷）

现状：`opmode` 第 0 段只接受两字符 `L0..L5` 或 `?`（`OverlayService.java:2559-2568`），标签显示「风控 中 · 操作方式 · 屏号」（`:2236-2241`）。

**要显示「已停风控」这种状态，只有两条路：**

| 方案 | 改哪 | 代价 |
|---|---|---|
| **A. 复用操作方式段**（推荐） | Node 侧把第 1 段写成 `已停·验证码` / `已停·用户叫停` | **只改 JS，不改浮窗**。操作方式本来就是自由文本（`vd.js:2244` 截 20 字）。浮窗每 3 秒读一次，10 秒内可见 |
| B. 加第四段状态 | Node 侧写 `L2\|拟人\|699\|stopped`；浮窗补解析 + `levelWord` 加新词 + `levelColor` 加新色 | 必须重编 `ai-overlay.apk`（`overlay/build.sh`），装机过程有一整套验证（`tools.js:1502-1545` 的 25 次轮询）。**改一半会让浮窗显示成默认白色**（`levelColor` 的 `default` 分支，`:2647`） |

**推荐 A**：在「已经出事」的场景下，用户要的是**时间效率**（10 秒内看到），不是排版好看。文字用「已停·验证码」五个字，21 字的操作方式段承载得了。

另外必须补的显示缺陷（第 17 条）：`refreshEdge` 不看端口 → 一块屏 `critical` 全局亮。**在风控场景里这条会被放大**——用户看到所有浮窗都红，以为全部出事。补法：`readEdge` 读第 6 段，和 `port` 比对，不等就回落待机。

### 3.6 检测可靠性的诚实评估

| 手段 | 会不会误报 | 会不会漏 | 建议 |
|---|---|---|---|
| 用户说停（events.log） | 不会 | 会（用户没点） | **永远信任**，优先级最高 |
| 焦点跳到系统窗口 | 会（登录页、广告页、系统权限对话框） | 会（自绘验证码） | 只在「非目标包**且** 画面变了」时判 SUSPECT，不直接判 TRIPPED |
| Activity 名黑名单 | 会（命名巧合） | 会 | 黑名单要短（5–8 个词），宁可漏 |
| OCR 关键词 | **会，而且不少**（微信聊天里「验证码」三个字一天几十次） | 会（WebView 自绘、小字、低对比） | 只在 SUSPECT 之后用，**不在每次点击后用** |
| 模板（滑块条） | 少 | 会（模板过期、尺寸变化） | 每个 App 单独做，明确写进「模板过期后失效」 |

**一句话：插件能做到「确认到你在风控页上」，做不到「判断你被风控了」。前者是可靠信号，后者要靠用户。**

## 4. 场景二：定级定高了怎么办

### 4.1 先定义「高」——用户说的「高」有两种

| 类型 | 表现 | 能不能降 |
|---|---|---|
| **保守定高**（L3 但其实没风控） | 写操作被拦、AI 每次都停下来问 | **能降，带证据** |
| **定义错误**（把 L2 当 L4/L5） | 整个包被禁 | 能降，但需要证据 + 用户确认 |
| **包本身带 forbid** | `risk.json:151-247` 的微信/支付宝/银行都是 `level:3, readOnly:true, forbid:["login","pay","face","write"]` | **不能降**。这里的「高」不是 AI 判断，是表里写死的禁止项。降级等于删掉「不碰支付」这条底线 |

**特别提醒**：`OPERATION-PLAYBOOK.md:163-173` 说「L3 只读，写操作交给人」，但 `risk.json` 里 L3 包的 `forbid` 已经把 `write` 列进去了 —— **表里 L3 的「写」是全禁，不是「问用户」**。这个不一致必须在实现前定下来（我建议：以 `forbid` 为准，`level` 只决定它有多敏感）。

### 4.2 「怎么发现定高了」——三种来源，按可信度

| 来源 | 可信度 | 理由 |
|---|---|---|
| **用户说「其实没这么严，直接操作」** | 最高 | 用户知道自己的账号历史（新号容易被风控、老号风控早淡了）—— 这正是 AI 拿不到的信息 |
| **AI 的读操作全都通过**（`vdisplay_shot`/`vdisplay_text` 正常、`ui` 能读到树、`launch` 正常） | 中 | **「读得到」不等于「写得进」**。对 L3（微信/支付宝），读从来不是风控触发点，这是 `PLAYBOOK.md` 的公理 3。**不能当降级证据** |
| **AI 做了一次「无害写操作」通过**（点赞→取消、加购→清空、翻到下一页） | 中低 | 这是 `PLAYBOOK.md:60-63` 的推荐做法，但一次通过没有统计意义；**而且它自己就可能触发风控** |

**判据（推荐）：**

```
可以降级  ⟺  ① 用户明确说了「可以降」 或「这个 App 没那么严」
          ② 且 降级后的等级 ≥ floor(pkg)
          ③ 且 账本 tippedCount(pkg) == 0
          ④ 且 降级是「试运行」，不是永久 —— 见 4.4
不能降级  ⟺  risk.json 里该包有 forbid 含 "pay"/"face"/"login"
          或 该包 tippedCount ≥ 1（刚出过事，不许降）
          或 等级差 > 1（一次只降一级）
```

### 4.3 「AI 自己发现操作都被拒了」→ 这不是定高了，是闸门在按规则执行

这是用户问题里最容易走偏的一点：**AI 被拒之后的第一冲动是「把等级改低」，而不是「按规则停下来问」。**

所以闸门返回的文本必须**消灭这个冲动**：

```
❌ 现在（推测的写法）：操作被拒绝（等级 L3）
✅ 应该写成：
   已拦截：L3 的包不允许写操作。
   · 这**不代表**定高了。你被拦是因为规则，不是因为被风控。
   · 如果你确实认为这个 App 没那么严，调 vdisplay_risk { pkg, level:"L2",
     reason:"...", downgrade:true, evidence:"用户说过这个 App 可以正常操作" }，
     并说明你要做的动作。
   · 被拒和触发风控无关，**不要**把「被拒」当成「被风控」的证据。
```

**必须写死的一条：AI 不能把「操作被拦」当作「触发风控」的计数来源。** 否则会形成「我拦你 → 你说被风控 → 自动升级 → 更拦」的自激循环。闸门要区分**「被规则拦」**和**「被风控拦」**，只让后者进账本。

### 4.4 降级机制：带证据 + 试运行 + 自动回落

```
vdisplay_risk { pkg, level:"L2", mode:"拟人点击", reason:"…",
                downgrade:{ to:"L2", evidence:"用户说可以正常操作 / 中文关键词说…",
                            trial: true, scope:"write" } }
```

状态机：

```
CURRENT(L3)
   │ AI 申请降级 / 用户口述降级
   ▼
TRIAL(L2)   —— 只在本次会话、只对 scope 内的动作有效（scope=write 时读不受影响）
   │                    │
   │ 连续 N 次写操作无风控信号   │ 任意一次触发风控
   │ 且用户没叫停                │
   ▼                            ▼
CONFIRMED(L2)               REVERTED(L3) + 账本记一条「曾降级到 L2 后触发风控」
   │                            │
   │ 用户改口/24 小时过期        │ 24 小时内拒绝任何再次降级
   ▼                            ▼
CURRENT(回到 default)        CURRENT(L3，且 tippedCount 不变但 downgradeBlocked=true)
```

**关键参数（建议值，都是推断，需要真机标定）：**

| 参数 | 建议 | 理由 |
|---|---|---|
| 一次降几级 | **只能降一级** | 定级本来就靠判断；一次降两级说明前面的判断错得厉害，应该重定而不是连降 |
| 试运行多久 | 一个任务会话内，或 50 次写操作 | 类似「第一次写操作选可撤销的」（`PLAYBOOK.md:62`）|
| 「无风控信号」的判据 | 试运行期间账本无新增 + 用户没叫停 | 不要求「主动探测」，只要求「没出事」|
| 降级失败后的锁定期 | 24 小时 | 尝试性推断，同 3.3(c) |

### 4.5 防止乱降（用户最担心的那条）

用户没说出口的担心是：**AI 为了省事直接降到 L0**。防法有四层：

| 层 | 机制 | 能不能绕过 |
|---|---|---|
| **下限（floor）** | `floor(pkg)` 由 `risk.json` 决定：有 `forbid` 含 `pay`/`face`/`login` → `floor=L3`（且 forbid 本身不能降）；`readOnly:true` → `floor=L3`；`unknown_level`（未收录）→ `floor=L3` | 不能（AI 没有接口改 floor） |
| **只降一级** | 从 L3 → L2 可以，L3 → L0 不行 | 不能 |
| **证据必填** | `downgrade.evidence` 必填，且写进账本（可被打工单/日志查） | 能填废话，但留痕 |
| **降级后进试运行** | 不是永久生效，出一次事就回滚 + 24 小时禁降 | 不能 |

**AI 想要 L0 的正确路径**：`vdisplay_risk { level:"L0", reason:"系统设置，无风控" }` 对**未收录的新包**也允许，前提是 `forbid` 为空且 `floor` 允许。所以 floor 规则里「未收录 → L3」要改成「未收录 → L3 **仅第一次**，用户确认后可降到 floor=L0」——否则计算器这类 App 也会被卡。**这是本设计里要用户拍板的一个取舍点。**

## 5. 场景三：定级定低了怎么办

### 5.1 怎么发现

| 来源 | 可靠性 | 说明 |
|---|---|---|
| **触发风控（S0–S4）** | 最高 | 这是主要路径，见 §3 |
| **预警信号**（还没有风控，但像） | 中低 | 见下表 |
| **用户说「这个 App 很严」** | 高 | 用户知道自己的账号 |

**预警信号（建议纳入，但**只升不拦**）：**

| 信号 | 怎么拿 | 价值 |
|---|---|---|
| 页面上出现 `验证`/`实名`/`为保障你的账号安全` 字样但还不是弹窗 | OCR | 升一级预警 |
| Activity 从 `MainActivity` 变成 `XxxAuthActivity`/`XxxVerify` | dumpsys | 升一级预警 |
| 输入框出现 `inputType` 为数字且长度 4–6（短信验证码框） | `vdisplay_ui` | 强信号，但 `ui` 不常调 |
| 同一页面连续 3 次 `changed:false` | `input` 返回值 | 噪音大，不建议 |

**【推断】预警不应该自动提升等级，只应该让 AI 看到一行提示**：「这个页面出现了『账号安全』字样，可能触发了风控前置检查，建议重新确认等级」——因为误报率不可控，自动升会让用户看到等级乱跳。

### 5.2 升级机制

```
        低等级运行（如 L1）
              │
     ┌────────┴─────────┐
     │ 预警信号           │ 确认风控（S0–S4）
     ▼                    ▼
 AUTO-BUMP(L1→L2)      HARD-RAISE(→max(当前,L3))
 · 只升一级             · 立即生效
 · 不改行为，只改提示   · 写操作全拦
 · 24 小时不重复升      · 浮窗 critical
     │                    │
     └────────┬───────────┘
              ▼
       RE-VERIFY（重新验证等级）
       · 用户回话后确认：「这个 App 现在是 L3，你要我只读，还是交给你？」
       · 用户同意后，等级才稳定下来（写入账本 state:CONFIRMED）
```

**「升了之后要不要重新验证」——要，而且是必须，理由两条：**

1. **自动升的等级是机器推的，不是 AI 判的**。用户明确说过「风控等级由 AI 判断，不是插件替它选」。自动升相当于插件替 AI 做了判断，破坏了这条产品原则。所以要有一个「AI/用户确认」的环节。
2. **不验证的话，一次误报会把等级永久抬高**，用户下次用同一个 App 会发现「怎么突然只能读了」。

**折中：硬升级即时生效（安全不能等），确认后的确认状态才写入账本长期生效。** 即：未确认的升级是「临时高等级」，24 小时无新增风控则自动回落到 AI 原判的值，并提示用户「刚才自动升到了 L3，是你之前判断的 L2，要改回吗」。

## 6. 场景四：等级的生命周期

### 6.1 什么时候重新评估

| 时机 | 频率 | 谁触发 | 是否重问用户 |
|---|---|---|---|
| **首次对这个包做写操作** | 一次 | 闸门 | 不需要（AI 自己判断，用户不被打扰） |
| **每次注入前** | 每次都查，但不重判 | 闸门 | 不 |
| **触发风控后** | 事件驱动 | 探测器 | 需要 |
| **用户改主意** | 随时 | 用户口述 | — |
| **App 升级后** | 版本号变化 | `dumpsys package` 读 `versionName` | 不需要（只重判 L0–L2，L3+ 保持） |
| **超期** | 见 6.2 | — | — |
| **每天/每小时定时** | **不建议** | — | — |

**为什么不要「每天重评」**：等级的意义是「用户和 AI 达成的判断」，定时重评等于每天把这个问题重新问一遍，用户会烦（`产品意图.md` 的「不打扰」原则）。

### 6.2 有效期

**建议：等级带「依据来源」，不同来源不同有效期。**

```
level : L2
source: "ai-inferred"（按类型推理）   → 有效期 7 天
source: "ai-tested"  （试过写操作）   → 有效期 3 天
source: "user-said"  （用户口述）     → 永久（直到用户改口或出风控）
source: "tipped"     （触发过风控升上来的） → 永久 + 只升不降
```

- 过期不删，只把等级降为 `?`（未评估），下一次 `input` 时提示 AI 重定。
- **用户口述的等级不过期**——这是用户的决定，不是插件的推断。

**为什么不给所有等级统一 3 天有效期**（用户提的方案）：好处是避免旧判断，坏处是「用旧判断」本身通常不危险（App 的风控不会三天内从 L0 变成 L3），而「三天后 AI 再乱定一次」的风险可能更大。**按来源分有效期比按时间一刀切更准。**

### 6.3 多 App 场景

**现状（关键问题）**：`_riskAssessment` 是单个变量（`vd.js:2223`），A→B 切一次，A 的等级就没了，回到 A 时浮窗显示「未评估」。

**设计：按 `displayId × pkg` 存**

```
ledger.levels = {
  "1333": {                       // displayId
    "com.tencent.mm":     { level: "L3", source: "user-said", at: ... },
    "com.android.settings": { level: "L0", source: "user-said", at: ... }
  },
  "1334": { ... }
}
```

- **切回 A 还用原来的**：是。切 App 不是「每一个新 App 要重定」，用户原话是「A 定了 L2，切到 B 要重定；切回 A 还用原来的吗」——答案是**用原来的**（他问这个就是在期待不用重定）。
- **不同屏的同一个包要不要共用**：**共用**。风控是按账号和设备，不是按屏。
- **同一个包在主屏和虚拟屏同时出现**：主屏操作不归插件管（`AGENTS.md` 硬规则），账本只在虚拟屏记录。

### 6.4 完整生命周期状态机

```
                  ┌──────────────┐
   首次操作该包    │  UNASSESSED  │  浮窗「未评估」  ? 
                  └──────┬───────┘
                         │ AI 调 vdisplay_risk（或闸门提示后调）
                         ▼
                  ┌──────────────┐
                  │   ASSESSED   │  有等级 + source + 有效期
                  └──────┬───────┘
        ┌────────────────┼─────────────────┬──────────────────┐
        │ 用户说太严      │ 触发风控          │ source 过期        │
        ▼                ▼                  ▼                  │
  ┌──────────┐    ┌────────────┐     ┌──────────────┐          │
  │ TRIAL_Lx │    │  TRIPPED   │     │  UNASSESSED  │◄─────────┘
  │ 试运行    │    │ 硬升 ≥L3   │     │  回到起点     │
  └──┬───┬───┘    └─────┬──────┘     └──────────────┘
     │   │              │ 2 次
 无风控  触发          ▼
     │   │        ┌──────────┐
     ▼   └──────► │  LOCKED  │  只认用户口述，AI 不能改
  ┌──────────┐    └────┬─────┘
  │CONFIRMED │         │ 用户解除
  │ 长期生效  │         ▼
  └────┬─────┘    ┌──────────┐
       │          │ CHECKED  │  可读、写需逐次批准
       └─────────►└──────────┘
```

**四条铁律（实现时不可违反）：**

1. **等级由 AI 判断，插件只提醒和显示**（用户 2026-11-24 原话）。
2. **触发风控后必须停**——这一条是 `risk.json:308-313` 已有规则，现在缺执行。
3. **等级只能由用户或「探测到的风控事实」改变**，AI 只能在用户授权下降低，且带证据和试运行。
4. **计数和账本不能被 AI 清空**，只能被时间窗和用户动作改写。

## 7. 实现顺序（按性价比，每条都有独立价值）

| 序 | 改什么 | 改动量 | 立刻解决 |
|---|---|---|---|
| 1 | **账本 + 闸门**：`input()` 里加 `gate()`，按 `pkg` 查有效等级、`forbid`、`tippedCount`；拒绝时返回「被规则拦，不是被风控拦」的文本 | 中 | 「定了等级没用」+ 防止 AI 把被拒当风控 |
| 2 | **`_riskAssessment` → 按 pkg 的 Map**（先不做 displayId） | 小 | 多 App 串值 |
| 3 | **持久化**：账本写 `/data/local/tmp/dshframe/risk.ledger` + 宿主 `~/.dsh/plugin-screen/risk-ledger.json` | 小 | 跨会话 |
| 4 | **S0 探测器**：`input()` 开头读一次 `events.log` 新行（复用 `pollUserEvents` 的判据，但不要它的「标记已读」，见 8.5），命中即拒 | 小 | 用户叫停 100% 生效 |
| 5 | **S1/S2 探测器**：`input()` 前一次 `dumpsys window`，焦点包 ≠ 目标包且像验证页 → SUSPECT | 中 | 系统验证码、WebView 验证页 |

## 8. 标【不知道】、需要真机或用户拍板的

1. **`/data/local/tmp` 重启后是否保留** —— 【不知道】。Android 12+ 官方说 `/data/local/tmp` 在重启后清理，但各家 ROM 行为不一（红魔/努比亚）。**没在本机验证过**，建议先写一个小文件重启验证。
2. **OCR 关键词在真实 App 上的误报率** —— 【不知道】。建议对 3 个包（微信聊天、拼多多搜索、B站）各跑 100 次 OCR，统计「验证码」出现次数，再决定 S3 要不要做。
3. **`dumpsys window` 能否稳定区分「验证码 WebView」和「普通 H5 页」** —— 【不知道】。`mFocusedApp` 在 WebView 验证码上是否换 Activity？取决于 App 实现。要拿拼多多/淘宝各抓一次。
4. **`refreshEdge` 端口过滤问题是否真的会导致多屏同亮** —— 【推断】代码可推，但**没在多屏下实测**。做一次「建两块屏、只对一块 `vdisplay_edge critical`」就能确认。
5. **降级失败后 24 小时锁定是否合适** —— 【推断】，没有依据。用户拍板。
6. **未收录包（新 App）的 floor 要不要一律 L3** —— 取舍点，用户拍板：一律 L3 会卡住 L0 工具类新 App（计算器）；不一律 L3 则新 App 首写无保护。
7. **`risk.json` 里 L3 的 `forbid` 含 `write` 与 `PLAYBOOK` 的「L3 只读，写问用户」不一致，以哪个为准** —— 必须拍板。
