# AI 操作 Android App 与网站 · 方式选择手册

> **读者**：任何要操作这台手机的 AI（或人）。
> **目的**：拿到一个目标，10 秒内判断「能不能做、用什么做、什么时候必须停」。
>
> **证据标注**：`【实测】`= 本机跑过；`【有依据】`= 框架/源码/标准里机制确定；`【推测】`= 有推理链但没在本机验证；`【不知道】`= 没查清，**别拿它做决定**。

---

## 三条公理

**公理 1：系统层必然暴露，环境层几乎不暴露。**
`deviceId`、虚拟屏 `displayId≠0`、`FLAG_SECURE` 这三样躲不掉【实测】；
而网络层 0 暴露、行为层 0 破绽、环境层只剩 `getCoalescedEvents` 恒 1【实测】。

→ **对强风控目标，「不被发现」是伪命题。只能选「被发现前做完」或「被发现也不亏」。**

**公理 2：不碰 UI 的路，成本和风险各低一个数量级。**
deeplink / content provider / dumpsys / 缓存文件 / CDP 读 DOM，都是毫秒到百毫秒级，且完全不产生触摸事件【有依据】。

→ **任何任务先问「有没有不碰界面的做法」，这一步能砍掉一半以上需求。**

**公理 3：风控等级决定投入上限，不决定成功率。**
对 L3（微信/支付/银行）做拟人化是纯浪费 —— 它的判定不在行为层。

→ **L3 以上不做拟人化，只做只读或交给人。**

## 一、六级速查表

| 级别 | 代表 | 核心检测点 | 推荐方式 |
|---|---|---|---|
| **L0 零** | 系统设置、文件管理、开源工具 | 无 | 命令直接改，不用点界面 |
| **L1 弱** | B站、YouTube、阅读器、播放器 | 服务端播放统计 | deeplink + OCR + tap |
| **L2 中** | 社交、电商、外卖、出行 | 指纹 SDK + 触摸属性 + 行为模型 | scrcpy 注入 + 拟人化 |
| **L3 强** | 微信、支付宝、银行、政务 | 设备绑定 + 完整性 + 无障碍 + 活体 | **只读**，写操作交给人 |
| **L4 极强** | 游戏反作弊、抢购、票务 | native 反作弊 + 账号权重 | **不做** |
| **L5 特殊** | DRM 内容、人脸实名 | Widevine、活体 | 媒体键 / 交给人 |

> 包名以实际安装为准，用 `pm list packages | grep <关键词>` 核对。
> **等级不确定时，按高一级处理。**

## 二、决策树（照着走）

```text
0) 这个操作失败，最坏结果是什么？
   ├─ 封号 / 资金损失 / 法律或实名风险 ──→ 停。交给人。
   └─ 只是重来一次 ──────────────────→ 继续

1) 有没有不碰 UI 的路？
   ├─ deeplink 能直达？ ────────────→ am start -d，完事
   ├─ 数据在 dumpsys / 缓存 / provider 里？ → 直接读
   ├─ 是网页？ ───────────────────→ CDP 读 DOM / Input.*
   └─ 都没有 ─────────────────────→ 第 2 步

2) 目标属于哪一级？
   ├─ L0 / L1 ──→ 直接注入，不拟人化，不上 OCR
   ├─ L2 ───────→ scrcpy 注入 + 拟人化 + 真机真 IP
   │              ├ 先只读观察 2-3 分钟
   │              ├ 第一次写操作选可撤销的（点赞→取消、加购→清空）
   │              └ 5 分钟内出现验证/限流 ──→ 停，交给人
   ├─ L3 ───────→ 只读（dumpsys / 截图+OCR / deeplink）
   │              写操作 ─────────────→ 交给人
   └─ L4 / L5 ──→ 不做（L5 的媒体键除外）

3) 出现验证码 / 二次验证 / 限流 / 风险提示？
   ├─ 第一次 ──→ 停当前做法，换一种，只再试一次
   └─ 第二次 ──→ 全停，回滚，交给人，记下触发条件

4) 连续同类操作 ≥ 20 次？
   └─ 是 ──→ 强制插 10-60 秒空闲，或直接停
```

### 四个「必须停」的硬条件

任何一个命中，**立刻停，不要换方式重试**：

1. 出现验证码 / 滑块 / 二次验证
2. 出现「账号异常 / 设备异常 / 操作频繁」提示
3. 目标是 L3 且动作是「写」
4. 同一目标第二次触发风控

## 三、十二种操作手段

| # | 手段 | 成本 | 隐蔽性 | 适用 | 关键缺陷 |
|---|---|---|---|---|---|
| 1 | `adb shell input` | 100-300ms | **低** | L0/L1 | 无 MOVE、压力恒定、deviceId=0/-1 |
| 2 | **scrcpy 注入** | 5-20ms/事件 | 中 | L2 及以下 | deviceId 仍非物理设备、coalesced 恒 1 |
| 3 | 无障碍 `dispatchGesture` | 300-800ms | 低 | L0/L1 | 无障碍服务会出现在系统列表 |
| 4 | 无障碍 `ACTION_SET_TEXT` | 400-1200ms | 中 | 表单后备 | 会开无障碍通道；占前台 |
| 5 | CDP `Runtime.evaluate` | 15-40ms | 中-高 | 读、填表 | `isTrusted=false`，React 可能不同步 |
| 6 | CDP `Input.*` | 10-30ms | **高** | SPA、需真实事件 | 要正确坐标 |
| 7 | **deeplink / intent** | 150-2000ms | **最高** | 能直达的一切 | 只能到入口 |
| 8 | `dumpsys` / `content` 读 | 100-600ms | **最高** | 状态、通知、数据 | 读不到 `/data/data` |
| 9 | **缓存文件读** | 50-200ms | **最高** | 媒体、日志 | 只读，不能写回 |
| 10 | `uiautomator dump` | 0.8-2.5s | 中 | L0/L1 取树 | 会暴露无障碍 |
| 11 | 截图 + OCR | 2.2-4.1s | 高 | L2+ 感知 | `FLAG_SECURE` 全黑 |
| 12 | **灰度变化检测** | **~0ms** | 最高 | 判断「稳了/生效了」 | 只知道「变了」，不知道「变成什么」 |

> 成本是量级【推测】，随负载/分辨率变化。OCR 的 1.9-3.3 秒、视频流 34fps 是本机实测【实测】。

### 关键要点

**1. `adb shell input` 是最假的**
没有 MOVE 序列、压力恒默认、无历史点、`getDeviceId()` 是 0 或 -1。
**对任何会读 `MotionEvent` 的 App 都是明牌。** 只在 L0/L1 用。

**2. scrcpy 控制通道是最强的无 root 注入**
它构造完整 `MotionEvent`（DOWN + N×MOVE + UP），能设压力/接触面积，可 60Hz 连发。
残留缺陷：`deviceId` 仍非物理设备、`getCoalescedEvents()` 恒 1【实测】。
**用法要点**：滑动必须自己生成 MOVE 序列（曲线 + 抖动），不能只发 DOWN/UP。

**7. deeplink 优先级最高**
完全不产生触摸事件，App 看到的是正常启动。
```bash
am start -W -a android.intent.action.VIEW -d "bilibili://video/12345"
```
局限：只能到入口，不能完成多步操作。

**12. 灰度变化检测是被低估的**
34fps 视频流上算帧差，成本近 0【实测】。
把「等 2 秒再 OCR」换成「等到画面稳定再 OCR」，能省一半时间。

## 四、哪个 App 属于哪一级

### L0 零风控
系统设置、文件管理、`is.xyz.mpv`、Termux、F-Droid、计算器、时钟、日历、相机。

**做法**：优先 `settings` / `cmd` / `am start`，根本不进界面。
**禁忌**：不要自动化「安全相关设置」（锁屏密码、指纹录入、adb 授权、恢复出厂）——这不是风控问题，是**会把用户锁在门外**。

### L1 弱风控
B站、YouTube、爱奇艺、优酷、微信读书、豆瓣、网易云音乐、喜马拉雅。

**做法**：deeplink 直达 + 媒体键（`KEYCODE_MEDIA_PLAY_PAUSE` 不走 UI，风控无关）。
**禁忌**：不要刷播放/点赞——那是服务端反作弊，与客户端手段无关。

### L2 中风控（最容易误判的一级）
微博、小红书、知乎、抖音、淘宝、京东、拼多多、闲鱼、美团、饿了么、滴滴、高德。

**它们检测什么**：
- **设备指纹**：OAID、AndroidID、Build 全字段、传感器列表、已装应用列表、屏幕参数。**我们的虚拟屏会改变「屏幕参数」和「显示 ID」，这是指纹里的一个不一致项。**
- **触摸属性**：`getDeviceId()`、`getToolType()`、`getCoalescedEvents()`、`getPressure()/getSize()`、`getHistoricalX/Y()`
- **无障碍与输入法**：`getEnabledAccessibilityServiceList()` 能拿到服务包名；`WindowInsets.Type.ime()` 能看出输入法有没有弹
- **行为模型**：点击间隔分布、滑动速度曲线、页面停留时长、请求序列
- **传感器**：点击瞬间加速度计有没有扰动

**做法**：
1. scrcpy 注入（有 MOVE、压力可设）
2. 先只读观察 2-3 分钟
3. 第一次写操作只做**可撤销**的
4. 触发一次验证 → 停，换一种只再试一次；第二次全停

**禁忌**：`adb input`、无障碍 `dispatchGesture`、新号第一天就自动化、固定节奏、批量 >20 次。

### L3 强风控（结论：只读）
微信、QQ、支付宝、云闪付、各家银行、交管12123、个税、12306。

**它们检测什么**：
- **微信**：Root/Xposed/注入检测、`/proc/self/maps` 扫可疑 so、调试器检测、TLS pinning（mmtls 私有协议）、设备指纹强绑定、多开检测、无障碍检测、屏幕共享/录屏检测
- **支付宝**：mPaaS + SecurityGuard、设备指纹、传感器、点击热区、屏幕镜像检测、人脸活体
- **银行**：TEE/KeyStore 设备绑定、Play Integrity、**自绘安全键盘（随机布局）**——坐标点击会被打乱
- **政务**：实名 + 人脸 + 定位 + 设备绑定 + 时段限制，多重叠加

**做法**：读只走 `dumpsys notification --noredact` / 截图+OCR / deeplink 到首页。**写一律交给人。**
**禁忌**：登录、支付、转账、改密、绑卡、开通、人脸——任何一项都不做；不要改设备标识（直接触发风控）；不要 hook。

### L4 极强（结论：不做）
王者荣耀、和平精英、原神、i茅台、大麦、猫眼、Nike SNKRS。

ACE / 易盾 / mHyProt：native 层轮询 `/proc`、ptrace 反调试、so 完整性、注入检测、模拟器/多开检测、输入事件来源、点击轨迹模型。
**一次封号可能连带实名进该平台黑名单，损失不可逆。**

### L5 特殊
**DRM**（Netflix、Disney+）：Widevine L1 + `FLAG_SECURE`，截图全黑。只能媒体键控制 + OCR。
**人脸实名**：交给人。用照片/视频糊弄活体是违法、必败、且留痕。

## 五、五分钟判定一个新 App 的等级

1. **看集成了什么 SDK**：`dumpsys package <包名> | grep -iE "safety|risk|secur|guard|shield|ace|integrity"`（SDK 名不一定会出现，仅作线索）
2. **静态扫关键词**：反编译搜 `isDebuggerConnected`、`getDisplayId`、`getCoalescedEvents`、`AccessibilityManager`、`FLAG_SECURE`
3. **只读观察 3 分钟**：看有没有「检测到无障碍/录屏/多开」提示
4. **一次无害写操作**：点赞→取消、加购→清空。触发验证就升级判定
5. **查公开案例**：搜「<App> 封号 / 风控 / 设备异常」

## 六、网站类型与操作方式

| 类型 | 代表 | 通道 | 关键点 |
|---|---|---|---|
| 静态/文档 | MDN、Wikipedia | `Runtime.evaluate` 读 DOM | 只读，无事件 |
| **SPA/React** | GitHub、Notion、Figma | 真实事件 / 无障碍打字 | **受控组件坑** |
| CF/风控验证 | 大量站点 | attach 真实浏览器 | **别伪造指纹** |
| 需登录态 | 后台、邮箱、云控制台 | 复用已登录 tab | 不新开、不重登 |
| 反爬严格 | 淘宝/京东/微博 web | 少量只读或放弃 | 别批量 |

### SPA / React 站：最常见的坑

直接 `el.value = "x"` **不触发 React 的 onChange**，提交后是空值。

```js
// 正解：native setter + 冒泡 input 事件
const set = Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set;
set.call(el, 'text');
el.dispatchEvent(new Event('input', { bubbles: true }));
```

**实测结论**：CDP 这条路在 GitHub 建 token 时**填值成功但提交不了**。
最后走通的组合是「CDP 查状态 + 无障碍通道打字 + 无障碍点提交」【实测】。

### 有风控验证的站：最大的优势是复用真实浏览器

`navigator.webdriver === false`，没有自动化痕迹。
**不要做的事**（做了反而露）：伪造 UA/时区/语言/WebGL/canvas 指纹——**与真实环境不一致是最强的检测信号**。

### 需要登录态的站

用已登录的 tab，**不新开、不重登、不清 cookie**。IP/UA/时区突变都会触发二次验证。

## 七、拟人化参数（起点值，需回归校准）

> **这些是【推测】起点值，不是实测结论。** 行为层的判据是「能不能过你自己写的检测器」，不是「看起来像」。

```json
{
  "tap": {
    "interval_ms": {"dist":"lognormal","median":380,"sigma":0.35,"clip":[180,1500]},
    "offset":      {"dist":"gaussian","sigma_ratio":0.30}
  },
  "swipe": {
    "duration_ms": {"dist":"lognormal","median":220,"sigma":0.40,"clip":[120,1200]},
    "curve":       {"type":"cubic_bezier","ctrl_offset_ratio":0.18,"perp_jitter_px":[8,15]},
    "speed":       {"profile":"ease_in_out","peak_px_s":[800,1500]},
    "tremor":      {"freq_hz":[6,11],"amp_px":[1.0,3.0]}
  },
  "long_press": {"dist":"mixture","components":[[0.70,[500,900]],[0.25,[900,1500]],[0.05,[1500,3000]]]},
  "pressure":   {"down":[0.25,0.45],"hold":[0.45,0.75],"up":[0.05,0.20]},
  "think":      {"new_screen_ms":[800,2500],"form_ms":[1200,4000],"before_submit_ms":[500,1200]},
  "typing":     {"char_interval_ms":[80,220],"word_pause_ms":[300,900]},
  "retry":      {"base_ms":3000,"factor":2.5,"jitter":0.40,"max_attempts":3},
  "session":    {"active_min":[3,8],"idle_s":[10,60]}
}
```

**为什么这么定**：
- **点击间隔用对数正态，不用均匀分布**。人的反应时是右偏的，均匀分布的矩和峰度都对不上【有依据】。
- **轨迹**用三次贝塞尔，控制点沿法线偏移 `距离 × 0.18`，端点叠 ±8-15px。
- **微抖动**叠 6-11Hz、1-3px 正弦 + 高斯噪声——真人手有生理性震颤。
- **长按用三峰混合**，不要恒定 500ms——恒定值最好抓。
- **压力**用 scrcpy 通道能设，`adb input` 设不了。

### 三条否决性规则

1. 任何两个动作间隔 **< 100ms** 都是非人类
2. 任何参数**恒定不变**（固定 sleep、固定坐标、固定时长）都是非人类
3. 连续 **≥20 次**同类操作必须停或插空闲

## 八、诚实边界：无论怎么拟人化都会被识破的

| 破绽 | 层级 | 能否绕过 |
|---|---|---|
| `getDeviceId()` 非物理设备 | 系统 | **不能**（无 root）【实测】 |
| `getCoalescedEvents()` 恒为 1 | 环境 | **不能**【实测】 |
| 虚拟屏 `displayId != 0` | 系统 | **不能** |
| `FLAG_SECURE` 截图全黑 | 系统 | **不能** |
| 点击时加速度计无扰动 | 传感器 | **不能**（无 root 无法伪造传感器）【推测】 |
| IME 不弹出 | 环境 | **不能**（`WindowInsets.Type.ime()` 可读）【推测】 |
| 无障碍服务出现在系统列表 | 应用 | 能（不用无障碍即可） |
| 设备绑定（银行/支付） | 服务端 | **不能** |
| 活体检测 | 硬件 | **不能** |
| 账号权重 | 服务端 | **不能**（只能养号） |

**一句话**：L3 以上，行为层做得再好也没用，因为判定发生在我们够不到的那几层。

## 九、应该直接放弃自动化的

- 微信 / 支付宝 / 银行的**登录、支付、转账、改密、绑卡、开通**
- 任何**人脸活体**
- **游戏竞技/排位**
- **抢购 / 票务**
- **政务实名业务**
- 任何「封号会连累实名身份」的场景
- **绕过未成年人防沉迷**（法律风险）

### 「值不值得自动化」判据

按顺序问，**任一条否决就停**：

1. **失败后果可逆吗？** 不可逆（钱、账号、数据、实名记录）→ 不做
2. **有人工兜底吗？** 全程无人可接管 → 不做
3. **一次性还是长期？** 一次性 → 交给人比开发快
4. **入口稳定吗？** 有 deeplink/API → 值得；纯 UI 点击 → 每次 App 更新就坏
5. **频次够吗？** 每天 1 次 → 手动；每天 100 次 → 自动化

```
ROI = (T_手动 − T_自动) × N
      ────────────────────────────────
      C_开发 + C_维护 + P_封号 × L_封号

N < 20 且 L_封号 > 0  →  不做
P_封号 > 0.1          →  不做
C_维护 > 每月 4 小时   →  不做
```

**经验规则**：如果任务「每周只做一次」，交给人永远比自动化划算 ——
因为自动化的真正成本不是开发，是**每次目标更新后的修复**。

## 十、反面案例库（比正面描述省时间）

```text
❌ adb input 点微信发送
   → deviceId=-1，账号进风控
   ✅ 改用 handoff

❌ web_fill 填 React 表单
   → 值被框架回滚，报「内容不一致」
   ✅ 改用无障碍通道打字（已验证 React 认）

❌ uiautomator dump 抓 L2 界面
   → 无障碍暴露，App 可能降级
   ✅ 改用截图 + OCR

❌ 失败立刻重试
   → 3 次内必触发验证码
   ✅ 按 3s → 7.5s → 19s 退避，第 3 次放弃

❌ 用首尾截图判断点击是否生效
   → 漏掉瞬时态，终态相同误判
   ✅ 改用帧计数时间线（watchFrames）

❌ 猜坐标点击
   → 点空了以为按钮坏了
   ✅ 先 OCR 定位，再用 aim.mjs 可视化校准

❌ 用 scrcpy 流判断画面是否在动
   → 循环论证
   ✅ 用 screencap 独立交叉验证
```

## 十一、本机实测能力清单

这些是**已验证可用**的，可以直接依赖：

| 能力 | 数据 | 备注 |
|---|---|---|
| 虚拟屏视频流 | **34 fps** | H.264 |
| 抓虚拟屏单帧 | 143ms/帧 | `screencap -d <SurfaceFlinger ID>` |
| 音频采集 | **184 KB/s，75% 非零** | `raw_stream=true`，纯 PCM |
| 本地语音转文字 | 五种语言全对 | SenseVoice，免费离线 |
| OCR | 1.9-3.3 秒 | 带归一化坐标 |
| 灰度传感器 | 7.6ms/帧 | 免费算变化 |

**两个必须记住的坑**：
- `screencap -d` 要 **SurfaceFlinger ID**（19 位大数），不是逻辑 displayId，连主屏的 `-d 0` 都不认
- 音频 socket 不加 `raw_stream=true` 时有 64 字节设备名头，按 12 字节跳会读成静音
