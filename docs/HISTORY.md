# 开发历程

> 这份文件记录这个项目**怎么来的、经历了什么、试错过什么**。
> 不是 changelog（那个看 `git log`），是「为什么变成现在这样」。

---

## 一、起点

**2026-11-06**，第一个提交：`feat: second screen for DSH Go (experimental v0.1.0)`

当时的想法很简单：DSH Go 是一个手机上的 AI 助手，但它操作手机时会**占用主屏**——
用户要么停下来看着它点，要么被打断。

如果能给它一块**看不见的第二块屏**，用户在主屏做什么都不受影响，这件事就成立了。

技术上，安卓有 `VirtualDisplay`，而 scrcpy 的 `new_display` 模式正好能做这件事。
所以起点是「scrcpy 的一个封装」。

---

## 二、需求定型（决定整个项目形态的一天）

需求是在开发过程中逐步说清楚的。作者原话：

> 「我的想法是**我刷我的视频、我在主屏幕做视频，而你在后台自己建一个屏幕
> 做我要求你的事情**，然后**我还能随时看得到**，**不想看到的时候也可以缩到最小**
> 就这么简单。」
>
> 「然后延伸出风控操作方式、工作时完成时出问题时会显示不同的边缘灯效，
> 然后还要**我不能打扰到你虚拟屏**，然后又延伸出一堆问题。」

这段话拆成了四条硬要求，写进了 `docs/产品意图.md`：

1. **双向不打扰** —— 用户的操作不影响虚拟屏，AI 的操作不影响主屏
2. **随时看得到** —— 浮窗实时显示
3. **随时能缩** —— 36dp 缩略图，收起后画面仍刷新
4. **状态能看出** —— 边缘光效

**这份文件后来成了整个项目的裁判。** 每次要加功能，先问「它服务这四条里的哪一条」。
对不上的就是跑偏了。

## 三、三个技术突破

### 突破 1：虚拟屏能建立，但会跟着进程死

**问题**：用 `node -e "..."` 建屏，命令一结束屏就没了。

**原因**：`VirtualDisplay` 的持有者是创建它的进程。进程退出 = 屏销毁。

**解决**：必须有一个**长驻进程**持有它。于是有了 daemon 形态，
后来又有插件形态（插件进程本身就是长驻的）。

**这个坑至今写在 AGENTS.md 第二条**：「虚拟屏会随创建它的进程一起死」。

### 突破 2：怎么让用户看见（浮窗）

**问题**：插件跑在 proot 里，拿不到 Android 的 `WindowManager`，画不了浮窗。

**解决**：拆出一个**独立 APK**（`com.dsh.overlay`），用
`TYPE_APPLICATION_OVERLAY` 盖在主屏上，通过本地 HTTP 从 framesrv 取 MJPEG。

**为什么不用别的方案**：
- VirtualDisplay 上画浮窗？不行，那是在虚拟屏上，用户看不见
- 用 `MediaProjection`？那是录屏，会一直提示
- 直接在 Node 里画？proot 里没有 WindowManager

### 突破 3：边缘灯效（从装饰变成状态通道）

**需求**：用户不想一直盯着浮窗看，所以需要「一眼知道 AI 什么状态」。

**第一版做成了单纯的彩色边框**，被指出两个问题：

1. **红绿色盲的问题**：只靠颜色区分，8% 的男性用户分不出
2. **AI 要主动调**：AI 会忘，忘了就不亮

**改法**：

- **颜色 + 运动双编码**：每档除了颜色不同，运动节奏也不同
  （weathered 匀速流动 / done 从左扫 / warning 慢呼吸 / error 双拍 / critical 低频闪）
- **working 和 done 全自动**：不依赖 AI，AI 只负责三种异常状态
- **critical 低于 3Hz**：避免触发光敏性癫痫

用户明确说过：「工作结束和工作中就不需要 AI 操作和控制边的颜色，
只有工作时出错或者其他情况时才有 AI 自己让这个边出现什么颜色」。

## 四、四个「看着对但实际不生效」的坑

这是这个项目最痛的教训，**同一个模式出现了 4 次**。

### 坑 1：`catch {}` 吞掉了 ReferenceError

```js
try {
  emptyStreak += 1;      // emptyStreak 没声明 → ReferenceError
} catch { /* ignore */ }  // 被吞掉
```

**后果**：整个看门狗从来没启动过。代码看起来完全正常。

### 坑 2：变量声明在错误的作用域

```js
function startIdleWatch() {
  let opBusy = 0;   // ← 每次调用都是新的局部变量
  ...
}
```

**后果**：grace period 永远不生效 → 看门狗在建屏进行中就把屏拆了。
这个 bug 出现了 **3 次**（不同变量）。

### 坑 3：`readFileSync` 读设备路径

```js
const state = readFileSync('/data/local/tmp/dshframe/opmode');
```

**后果**：proot 里没有这个路径，ENOENT 被 catch 吞掉，**静默永远不执行**。

**修法**：所有设备文件访问必须走 `adb shell cat`，而且是异步的。

### 坑 4：限帧变量从没被赋值

```js
let lastDrawAt = 0;
// 每帧：if (now - lastDrawAt < 1000/30) return;
// 但从来没写 lastDrawAt = now
```

**后果**：限帧完全失效，实际跑满 60fps。

### 教训

**「代码看起来对」和「它真的在执行」是两件事。**

后来写进了 `AGENTS.md`：任何自动机制，必须验证它真的跑了。

## 五、一个假 bug 浪费了半天

**现象**：虚拟屏跑一段时间后画面全黑。

**当时的判断**：`mHasContent` 字段变成 false 了，说明屏没内容了。

**修法**：加了个看门狗——「连续 3 次 mHasContent=false 就重建屏」。

**结果**：用户画面开始乱跳，浮窗里的 App 反复重启。

**实测发现**：

```
mHasContent 对所有虚拟屏永远是 false
——包括正在正常显示拼多多聊天界面的那块
```

**所以那个看门狗每 30 秒把一块好屏拆一次。**

**更糟的是「修法」比原 bug 更危险**：
- 重建走 `T.start({})` → 自动 `pickHomeLike` + `am force-stop`
  → **把用户屏上的 App 换成计算器**
- `markLost` 只清状态不 stop → 旧屏和 encoder 全部泄漏，每 100 秒一块

**最终决定：整段删除。** 理由写进了代码注释：

> 「这个机制的收益（修一个未被证实的黑屏）远小于风险（拆好屏+换App+泄漏）」

**这是「宁可少一个功能，不能多一个会自己坏的机制」的来源。**

## 六、对抗审查抓出的真 bug

项目里有多轮独立对抗审查。**它们抓出的 bug 比写的代码更有价值。**

几个典型：

### `am start --display` 会搬走主屏任务

**原以为**：只有 `singleTask` 的 App 会中招。

**逐行读 AOSP 才发现**：

```
am start 无条件加 NEW_TASK
→ resolveReusableTask: putIntoExistingTask = (NEW_TASK && !MULTIPLE_TASK) || singleTask
→ findTask 遍历【所有】显示器找已有任务
→ 找到就 reparent 到目标屏
```

**结论**：standard/singleTop 一样中招。

**这直接否掉了一个「优化方案」**（去掉 force-stop 避免杀用户 App）——
真相是：去掉 force-stop 只是把「杀进程」换成「搬任务」，用户 App 照样消失。

### 一个没用的属性造成了最大的暴露面

**背景**：为了 3D 游戏在虚拟屏渲染，每次建屏都 `setprop debug.sf.enable_hwc_vds 1`。

**两个实测发现**：

1. **它没用** —— SurfaceFlinger 已连续运行 17 天没重启，而 AOSP 里这个属性
   只在 SF 构造函数读一次。置 1 后 `dumpsys SurfaceFlinger` 相关状态变化 = 0 处。

2. **它危险** —— 写了个探针 App（普通 App，零特殊权限），反射
   `SystemProperties.get` 直接读到了这个属性，还能看到 0→1 的变化。
   属性名里直接写着 `vds`（virtual displays）。

**教训**：一个没用的属性，换来了「这台机器在开虚拟屏」的铁证。

### 虚拟屏对 App 可见（这是设计限制）

用探针实测：

```
原版 scrcpy jar：  getDisplays() count=2
                  显示一块叫 scrcpy、属主是 com.android.shell 的虚拟屏

改过 flags 之后：  getDisplays() count=1
                  只剩主屏
```

**能隐藏，但代价是别的 App 也进不去**：AOSP 的 `Display.hasAccess`
用同一个判据决定「能不能渲染」和「能不能枚举」，做不出「能渲染但看不见」。

而且有个 present-UID 例外：**App 一旦跑到那块屏上，它自己就能枚举到**。

## 七、QQ 掉线事件（2026-11-21 → 11-24）

**这是项目转向的转折点。**

开发过程中，作者的 QQ 被腾讯强制下线 4 次。安全中心明确写：

> **风险类型：设备存在外挂或其他软件影响 QQ 正常使用**

### 排查过程

**排除法**：

```
❌ 进程被杀     → QQ 主进程活 1h56m、MSF 活 1d12h，无 force-stop 记录
❌ 密码问题     → 改密是 11-22，但问题 11-21 就开始了
❌ Root/Xposed  → 设备上没有
❌ 截图检测     → Android 14/15 官方明确不检测截图（含 ADB）
❌ 系统优化杀后台 → logcat 明确 Don't kill pkg com.tencent.mobileqq
```

**找出的暴露面**（全部实测）：

1. 虚拟屏对所有 App 可见，名字直接叫 `scrcpy`，属主是 shell
2. `debug.sf.enable_hwc_vds` 属性 App 可读（**已删除**）
3. ADB over TCP 开着（工具固有）
4. 浮窗遮挡（未实测）

**根因未完全确定。** 但删掉那个没用的属性是「零成本」的改动 —— 它既没用又危险。

### 影响

这件事让作者决定**停止使用这个项目**，并**开源出去**：

> 「把这些功能都关掉吧，我不用了，风险太大了。」

完整证据链见 [`docs/QQ掉线调查.md`](QQ掉线调查.md)。

## 八、为什么开源

作者的原话：

> 「开源吧，整理成可以让别人直接用的那种，包括非常详细的 readme 等等一系列的东西，
> 最好是能把我的思路包括发展历程都写进去，就是让人一看就知道这个东西是怎么来的，
> 经历了什么。让 AI 直接看文档就能接手开发的那种。
> 开源出去，然后如果以后有人想要商业化可以找我授权。」

所以：

- 代码用 **AGPL-3.0**（保持开源，同时保留商业授权空间）
- 文档写成「接手即用」的标准
- 风险如实写出来，不粉饰

## 九、如果继续做，下一步是什么

按优先级：

1. **搞清楚 QQ 到底读什么信号** —— 用小号做对照实验，不要拿主账号试
2. **浮窗信息自动化** —— 现在风控等级和操作方式部分依赖 AI 主动填，
   AI 会忘。应该由浮窗自己识别
3. **精简** —— 40 个工具、多屏池、租约、OCR/OpenCV 常驻，
   按「产品意图」看有一半不是为了核心场景存在的
4. **稳定性** —— 删掉所有判据不可靠的「自动修复」机制

**不要做的事**：继续加功能。这个项目的教训是
「每加一个自动机制，就多一个会自己坏的东西」。
